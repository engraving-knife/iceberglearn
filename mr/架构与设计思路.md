# iceberg-mr 模块架构与设计思路

> 本文档由源码注释整理生成，描述 `iceberg-mr` 模块的设计架构与设计思路。

## 1. 模块定位

`iceberg-mr` 是 Iceberg 与 **Hive / MapReduce 生态**的集成模块，处于引擎层与 Iceberg 核心层之间。它向下依赖 `iceberg-api`/`iceberg-core`/`iceberg-data`/`iceberg-parquet`/`iceberg-orc`/`iceberg-hive-metastore`，向上为 Hive 查询引擎、MR v1/v2 作业、Tez 引擎提供统一的 Iceberg 表读写能力。

它在 Iceberg 整体分层中的位置：

```
        Hive 执行引擎 / MR 作业 / Tez
                  │
        ┌─────────▼─────────┐
        │    iceberg-mr     │  ← 本模块：Hive StorageHandler / SerDe / InputFormat / OutputFormat / Committer
        │  (Hive/MR 适配层)  │
        └─────────┬─────────┘
                  │
   iceberg-core / iceberg-data / iceberg-parquet / iceberg-orc / iceberg-hive-metastore
                  │
              iceberg-api
```

核心职责：

- 把 Hive 的 DDL/DML/查询语义映射到 Iceberg 表生命周期（建表、删表、读写、提交）。
- 为 MR v1（mapred）与 v2（mapreduce）两套 API 提供 Iceberg 表的 InputFormat/RecordReader/Split。
- 把 Hive 谓词（SearchArgument）转换为 Iceberg Expression，实现谓词下推到文件层。
- 实现 Hive SerDe 体系与 Iceberg 类型系统之间的双向映射。
- 提供写入路径的两阶段提交（task 写数据 + forCommit 元数据，job 阶段统一 append 到 Iceberg 表）。

## 3. 核心类与设计模式

### 3.1 配置中心：`InputFormatConfig`

集中定义所有 Hadoop Configuration 键名（表定位、过滤、投影、提交、catalog、时间旅行等），并提供 `ConfigBuilder` 链式构造器封装常用配置组合。

**设计模式**：Builder 模式。构造时设置一组合理默认值（`SKIP_RESIDUAL_FILTERING=false`、`CASE_SENSITIVE=true`、`REUSE_CONTAINERS=false`、`LOCALITY=false`），并提供流式 API（`filter`/`project`/`select`/`readFrom`/`snapshotId`/`asOfTime`/`useHiveRows`/`usePigTuples` 等）。

**`InMemoryDataModel` 枚举**区分三种内存数据模型：`PIG`（Pig Tuple）、`HIVE`（Hive 行/向量化）、`GENERIC`（Iceberg GenericRecord，默认）。该枚举贯穿整个读取链路，决定 RecordReader 返回的对象类型与可用的文件 reader。

### 3.2 Catalog 门面：`Catalogs`

为 Hive/MR 集成层提供统一的 catalog 加载与表 CRUD 接口，屏蔽底层 catalog 实现差异。

**设计要点**：

- 区分两种寻址方式：**命名 catalog**（hive/hadoop/catalog-impl）按 `TableIdentifier` 寻址；**基于路径的表**（`location_based_table`）跳过 catalog 直接用 `HadoopTables` 按路径加载。
- 类型解析优先级：先按 `iceberg.catalog.<catalogName>.type` 解析；为 `location_based_table` 时视为无 catalog；type 为 null 时回退到 `catalog-impl` 指定的实现类；未指定 catalogName 时从全局 `iceberg.catalog.type` 读取。
- 把控制属性（schema/spec/location/name/catalogName）从最终交给 Iceberg 的属性表中剔除，避免污染表属性。

### 3.3 读取核心：`IcebergInputFormat<T>`

MR v2 InputFormat，是所有 Iceberg 读取路径的底层实现。被 `MapredIcebergInputFormat`（v1 适配）与 `HiveIcebergInputFormat`（Hive 适配）继承复用。

**`getSplits`**：

1. 优先从 StorageHandler 序列化的配置加载 Table（避免 executor 重新访问 catalog），否则用 `Catalogs.loadTable` 加载。
2. 构建 `TableScan`：设置 caseSensitive、snapshotId（时间旅行）、asOfTime、splitSize、读 schema 投影、列选择、过滤表达式。
3. 调用 `TableScan.planTasks()` 规划 `CombinedScanTask`，包装为 `IcebergSplit`。
4. HIVE/PIG 模式不支持残留过滤，提前 `checkResiduals` 校验残留谓词，发现未满足的直接报错。
5. 对 `DataTableScan`，按需跳过 FileIO 配置序列化以减小 split 体积。

**`IcebergRecordReader`**：顺序读取 split 内多个 `FileScanTask`，按文件格式（Avro/ORC/Parquet）打开数据文件，应用 equality delete 过滤与残留谓词过滤。

**设计模式**：

- **策略模式**：按 `InMemoryDataModel` 与文件格式选择不同的 reader 构造策略（`newAvroIterable`/`newOrcIterable`/`newParquetIterable`）。
- **反射解耦**：Hive 向量化 reader 类通过 `DynMethods` 反射加载，避免对 Hive 3 专用类的编译期依赖，从而同一份代码兼容 Hive 2/3。
- **可选序列化优化**：表对象通过 `SerializableTable.copyOf` 转为可序列化形式写入 split；可选跳过 FileIO 配置序列化以减小体积，反序列化侧通过 `checkAndSetIoConfig` 重新注入。

### 3.4 切分体系：`IcebergSplit` / `IcebergSplitContainer` / `HiveIcebergSplit`

- `IcebergSplit` 同时继承 v2 `InputSplit` 与实现 v1 `InputSplit`，一个切分类型可被两套 API 使用。携带 `Table` + `CombinedScanTask`，通过 `SerializationUtil` 做字节序列化传输到 executor。
- `IcebergSplitContainer` 标记接口：让外层包装 split（如 Hive `FileSplit`）暴露内部 `IcebergSplit`。
- `HiveIcebergSplit` 继承 Hive `FileSplit` 以满足 Hive 调度要求，`getPath()` 返回表 location 便于 Hive 反查 `TableDesc`。

**设计模式**：装饰器/适配器模式。`HiveIcebergSplit` 装饰 `IcebergSplit`，对外暴露 Hive 期望的 `FileSplit` 接口。

### 3.5 MR v1 适配：`MapredIcebergInputFormat` / `AbstractMapredIcebergRecordReader`

核心切分/读取逻辑只实现一次（v2），通过本层做 v1 → v2 API 适配，避免双份代码。把 `JobConf`/`Reporter` 包装为 v2 `JobContext`/`TaskAttemptContext`。

**`CompatibilityTaskAttemptContextImpl`** 额外持有老版 `Reporter` 引用，供 Hive 向量化 reader 等需要 Reporter 的场景使用。`toStatusReporter` 把老版 `Reporter` 适配为 v2 `StatusReporter`。

### 3.6 Hive 集成入口：`HiveIcebergStorageHandler`

实现 `HiveStoragePredicateHandler` + `HiveStorageHandler`，是 Hive 识别 Iceberg 表的核心适配器，串联 InputFormat/OutputFormat/SerDe/MetaHook/谓词下推。

**设计要点**：

- 在 `configureInputJobProperties`/`configureOutputJobProperties` 阶段，把表信息（schema、location、序列化的 Table 对象、catalog 名）写入 job 配置，分发到 executor。
- `decomposePredicate` 把 Hive 谓词同时作为 pushed/residual 返回，让 Hive 与 Iceberg 各自做裁剪（取两者并集效果）。
- **`overlayTableProperties`**：把 `Table` 通过 `SerializableTable.copyOf` 转为可序列化形式，base64 写入配置；移除 `columns.comments`（含 `\0` 分隔符会导致 job.xml 序列化失败）；把 schema JSON 也写入 tableDesc 属性，避免 SerDe 初始化时反复访问 HMS。
- **多表 insert**：用 `..` 分隔表名写入 `OUTPUT_TABLES`；`WRITE_KEY` 同时写入 map 与 tableDesc 属性，确保 SerDe 能在表级别判断是写路径。

### 3.7 Hive 读取入口：`HiveIcebergInputFormat`

继承 `MapredIcebergInputFormat`，复用核心切分与读取逻辑，本类只负责 Hive 适配。

**职责**：

- 把 Hive 下推的过滤条件（AST → `SearchArgument`）通过 `HiveIcebergFilterFactory` 转换为 Iceberg Expression，序列化到 JobConf。
- 读取 Hive 列裁剪信息写入 `SELECTED_COLUMNS`。
- 声明 `CombineHiveInputFormat.AvoidSplitCombination`，避免 Hive 合并 split 破坏 Iceberg 自身的并行度（`shouldSkipCombine` 恒返回 true）。
- 支持向量化执行（Hive 3+），通过 `DynConstructors` 反射加载 `HiveIcebergVectorizedRecordReader`。
- 过滤转换失败时降级为"不带 Iceberg 过滤"，由 Hive 自身做残留过滤，保证查询仍能跑通。

### 3.8 谓词转换：`HiveIcebergFilterFactory`

把 Hive `SearchArgument` 表达式树递归翻译为 Iceberg `Expression`。

**设计要点**：

- 递归处理 OR/AND/NOT/LEAF/CONSTANT 五种节点。
- 叶子谓词按 `PredicateLeaf.operator` 分支：EQUALS（含 NaN 特判）、LESS_THAN、LESS_THAN_EQUALS、IN、BETWEEN（拆成 `>= AND <=`）、IS_NULL。
- **NaN 特殊处理**：当 EQUALS 字面量为 NaN 时，Iceberg 用 `isNaN`（因为 `NaN != NaN`）。
- **时区与精度兼容**：Hive 内部使用 `java.util.Date` 走默认时区，会丢失微秒；通过反射读取 `PredicateLeafImpl` 的 `literal` 字段（绕过 Kryo 反序列化的 Date→Timestamp 转换），再用 `LocalDateTime` 还原，避免时区与精度问题。

### 3.9 Hive 写入路径

#### `HiveIcebergOutputFormat`

实现 `OutputFormat` 与 `HiveOutputFormat` 双接口，两个 writer 创建路径最终都委托给同一个 `writer(JobConf)` 方法，避免逻辑重复。文件格式、目标文件大小等参数取自 Iceberg 表属性，保持与 Iceberg 引擎本身一致的行为。

#### `HiveIcebergRecordWriter`

继承 `PartitionedFanoutWriter`，按分区键路由记录到不同的 appender，达到目标大小后滚动出新文件。同时实现 Hive `FileSinkOperator.RecordWriter` 与 MR `RecordWriter` 双接口。

**设计要点**：

- 复用 `PartitionKey` 对象避免每条记录都创建新对象。
- 静态 `writers` map 用并发 map（`TaskAttemptID -> (表名 -> writer)`），因为 Tez 等引擎会共享容器，需要线程安全。
- `close(abort=true)` 时并行删除已写出的数据文件，使用 worker 池加速。

#### `HiveIcebergOutputCommitter`

独立于 Hive ACID 事务的提交器，采用**两阶段提交**：

1. **任务级（commitTask）**：把每个任务生成的 `DataFile` 列表序列化为 `.forCommit` 文件，落到表 temp 目录。
2. **作业级（commitJob）**：并行收集所有任务的 `.forCommit` 文件，按目标表聚合后调用 `AppendFiles` 提交到 Iceberg 表。
3. **中止/清理**：`abortTask`/`abortJob` 删除已生成的数据文件与临时目录。

**设计要点**：

- `.forCommit` 文件按 `task-<id>.forCommit` 命名，job 阶段按预期任务数顺序读取，假设 taskId 从 0 连续生成。
- 两个线程池：`fileExecutor` 读 forCommit 文件，`tableExecutor` 并行处理多表，大小均可由配置控制；`tableExecutor` 在单表时返回 null 避免无谓线程开销。
- 任务失败容忍：用 `Tasks` 提供的 retry/suppressFailure 控制不同阶段的失败语义。
- 支持 Tez/MapReduce 两种执行引擎（通过 `TezUtil` 适配 ID 差异）。

#### `TezUtil`

专门处理 Tez 与 MR 在 `TaskAttemptID`/`JobID` 表示上的差异。`TaskAttemptWrapper` 重写 equals/hashCode，使 task type（map/reduce）不参与比较，从而 mapper 与 reducer 线程能用同一个 attempt ID 作为 key 复用 writer 缓存。

### 3.10 Hive SerDe：`HiveIcebergSerDe` + `Deserializer` + ObjectInspector 系列

#### `HiveIcebergSerDe`

Hive 读写 Iceberg 表的字段映射枢纽。

**initialize 多场景处理**：Hive 会在多处调用本方法（建表时 HiveDDL、编译期 HiveServer2、执行期 executor），通过 `serDeProperties` 内容区分场景：

- 优先使用 `TABLE_SCHEMA`；否则 `Catalogs.loadTable` 加载；都失败回退到 Hive schema。
- 写路径（`WRITE_KEY` 存在）不做投影下推；读路径按列裁剪做投影，且去重后再投影（同表多次 join 会导致列名重复）。
- `deserializers` 按 ObjectInspector 缓存，避免重复构建 schema 访问器树。

#### `Deserializer`

把 Hive 行对象转换为 Iceberg `Record`，被 `HiveIcebergRecordWriter`/`HiveIcebergSerDe` 使用。

**设计模式**：访问者模式。使用 `SchemaWithPartnerVisitor` 按结构同构地遍历 Iceberg schema 与 Hive ObjectInspector，把"每个字段的取值逻辑"编译成 `FieldDeserializer` lambda，避免每次反序列化都重新反射。

- **双 inspector 模式**：`sourceInspector` 用于从 Hive 行里取原始值；`writerInspector` 仅在需要类型适配时（实现 `WriteObjectInspector`）调用 `convert`。
- **`FixNameMappingObjectInspectorPair`**：Hive 查询结果列名可能与 Iceberg 列名不一致，但列顺序对齐，按位置建立名字映射。
- struct 反序列化复用 `GenericRecord.copy()` 作为模板，省去 `NAME_MAP_CACHE` 查找，提升性能。

#### ObjectInspector 系列

`IcebergObjectInspector` 继承 `TypeUtil.SchemaVisitor`，借助已有的 schema 遍历框架按结构同构地生成 ObjectInspector 树。

- 基本类型：BOOLEAN/INT/LONG/FLOAT/DOUBLE/STRING 走 Hive 标准实现；BINARY/FIXED/UUID/DATE/TIME/TIMESTAMP/DECIMAL 走 Iceberg 自定义实现。
- 处理 Hive 2 / Hive 3 在 Date/Timestamp ObjectInspector 上的 API 差异：通过 `DynMethods` 反射加载对应版本的实现类（Hive 3 走 `*Hive3` 后缀类，定义在 `hive3` 模块）。
- struct 字段名统一转小写，匹配 Hive 列名大小写不敏感的约定。
- `WriteObjectInspector` 接口区分写入路径的类型转换契约。

### 3.11 HMS 生命周期：`HiveIcebergMetaHook`

实现 `HiveMetaHook`，在 HMS 表创建/删除前后插入 Iceberg 侧动作。

**设计要点**：

- 同时支持 HiveCatalog 与非 HiveCatalog（HadoopTables 等）：HiveCatalog 模式下 Iceberg 表元数据存于 HMS；非 HiveCatalog 模式下 HMS 仅作"影子目录"，需要单独建表。
- schema 优先级：用户显式提供的 schema/spec 优先；否则由 HMS 列定义转换生成。
- 清理路径分两支：HiveCatalog 由 HMS 管理 metadata 目录，仅删数据；非 HiveCatalog 直接调 `Catalogs.dropTable` 删表。
- 异常容忍：drop 阶段的异常不应阻断 HMS 删表命令，因此 catch 后只告警。
- 非 HiveCatalog 时设置 InputFormat/OutputFormat 以便其他引擎（如 Impala）识别。

## 4. 关键流程

### 4.1 Hive 读取 Iceberg 表

```
Hive LOAD/SELECT
   │
   ▼
HiveIcebergStorageHandler.configureInputJobProperties
   │  序列化 Table(schema/location/serialized table) 到 job 配置
   ▼
HiveIcebergInputFormat.getSplits
   │  1. Hive AST -> SearchArgument -> HiveIcebergFilterFactory -> Iceberg Expression
   │  2. Hive 列裁剪 -> SELECTED_COLUMNS
   │  3. super.getSplits -> IcebergInputFormat.getSplits
   │     - 加载 Table（优先从序列化配置，否则 Catalogs.loadTable）
   │     - 构建 TableScan（时间旅行/投影/过滤/splitSize）
   │     - planTasks -> CombinedScanTask -> IcebergSplit
   │  4. 包装为 HiveIcebergSplit（携带 tableLocation）
   ▼
HiveIcebergInputFormat.getRecordReader
   │  - 向量化？反射构造 HiveIcebergVectorizedRecordReader
   │  - 否则 super.getRecordReader -> MapredIcebergRecordReader
   ▼
IcebergRecordReader.initialize / nextKeyValue
   │  - 按 FileScanTask 顺序打开文件
   │  - 按 format (Avro/ORC/Parquet) + InMemoryDataModel 选 reader
   │  - GENERIC: GenericDeleteFilter 过滤 equality delete
   │  - applyResidualFiltering: 残留谓词过滤
   ▼
Container<Record> -> HiveIcebergSerDe.deserialize -> Hive 行
```

### 4.2 Hive 写入 Iceberg 表

```
Hive INSERT
   │
   ▼
HiveIcebergStorageHandler.configureOutputJobProperties
   │  - 序列化 Table 信息
   │  - 设置 mapred.output.committer.class = HiveIcebergOutputCommitter
   │  - WRITE_KEY="true" 写入 map 与 tableDesc
   ▼
HiveIcebergStorageHandler.configureJobConf (MR 模式)
   │  - 表名追加到 OUTPUT_TABLES（".." 分隔）
   ▼
HiveIcebergOutputFormat.writer
   │  - 加载 Table/schema/spec/fileFormat/targetFileSize
   │  - 构造 OutputFileFactory（operationId = queryId + jobId）
   │  - new HiveIcebergRecordWriter（注册到静态 writers map）
   ▼
HiveIcebergRecordWriter.write
   │  - 从 Container 取 Record
   │  - PartitionedFanoutWriter 按 partition 路由到 appender
   │  - 达到 targetFileSize 滚动新文件
   ▼
HiveIcebergOutputCommitter.commitTask
   │  - tableExecutor 并行处理每个目标表
   │  - writer.dataFiles() -> createFileForCommit 序列化为 .forCommit
   ▼
HiveIcebergOutputCommitter.commitJob
   │  - fileExecutor 并行读所有 .forCommit
   │  - tableExecutor 并行 commitTable: AppendFiles.appendFile.commit()
   │  - cleanup 删除临时目录
```

### 4.3 Hive 建表

```
CREATE TABLE ... STORED BY 'org.apache.iceberg.mr.hive.HiveIcebergStorageHandler'
   │
   ▼
HiveIcebergMetaHook.preCreateTable
   │  - 设置 table type = ICEBERG
   │  - 非 HiveCatalog: 设置 InputFormat/OutputFormat；检查已有表
   │  - 计算 schema（用户显式 > HMS 列转换）与 spec
   │  - 分区键合并进列列表
   │  - 序列化 schema/spec 到 catalog 属性
   ▼
HMS 建表
   │
   ▼
HiveIcebergMetaHook.commitCreateTable
   │  - icebergTable == null 时调 Catalogs.createTable
   │  - HiveCatalog 模式设置 ENGINE_HIVE_ENABLED
```

## 5. 与其他模块的关系

| 关系模块 | 依赖方向 | 说明 |
|---|---|---|
| `iceberg-api` | 向下依赖 | Catalog/Table/Schema/Expression 等核心抽象 |

## 6. 设计亮点与权衡

### 6.1 单次实现 + 双 API 适配

核心切分/读取逻辑只在 MR v2（`IcebergInputFormat`/`IcebergRecordReader`）实现一次，v1（`MapredIcebergInputFormat`/`AbstractMapredIcebergRecordReader`）通过包装 JobConf/Reporter 为 v2 Context 做适配。`IcebergSplit` 同时实现两套 InputSplit 接口。这避免了维护两份代码，是本模块最重要的复用决策。

### 6.2 反射解耦跨版本兼容

Hive 2 与 Hive 3 在 Date/Timestamp ObjectInspector、向量化 reader 上有 API 差异。本模块通过 `DynMethods`/`DynConstructors` 反射加载 Hive 3 专用类（向量化 reader、Hive3 ObjectInspector），使同一份 mr 代码能编译并运行在 Hive 2 上，Hive 3 专属能力在 `hive3` 模块中提供并在运行期按 `HiveVersion` 选择性激活。

### 6.3 序列化优化与配置注入

表对象通过 `SerializableTable.copyOf` 转为可序列化形式写入 split/job 配置，避免 executor 重新访问 catalog。进一步可通过 `CONFIG_SERIALIZATION_DISABLED` 跳过 FileIO 配置序列化以减小体积，反序列化侧通过 `checkAndSetIoConfig` 重新注入 Hadoop Configuration（仅当 FileIO 实现 `HadoopConfigurable`）。这是体积与正确性之间的可控权衡。

### 6.4 谓词下推的"双裁剪"策略

`decomposePredicate` 把 Hive 谓词同时作为 pushed 与 residual 返回，即 Hive 与 Iceberg 都做裁剪，取两者并集效果。Iceberg 侧利用文件统计信息裁剪数据文件，Hive 侧做最终行级过滤。对于 HIVE/PIG 模式（不支持残留过滤），提前 `checkResiduals` 校验，发现未满足的残留谓词直接报错，避免读到不该返回的行。

### 6.5 两阶段提交的容错设计

写入路径采用 task 写数据 + forCommit 元数据、job 阶段统一 append 的两阶段提交。`.forCommit` 文件按 taskId 顺序命名，job 阶段按预期任务数并行读取。abort 路径并行删除已生成文件，删除失败仅告警不阻断。`Tasks` 工具的 retry/suppressFailure 控制不同阶段的失败语义，兼顾可靠性与可用性。

### 6.6 多表 insert 的隔离

通过 `..` 分隔表名写入 `OUTPUT_TABLES`，`WRITE_KEY` 同时写入 map 与 tableDesc 属性（map 中的属性会出现在所有表的 serde 配置中，无法区分），确保 SerDe 能在表级别判断写路径并跳过投影下推。`tableExecutor` 并行处理多表提交。

### 6.7 谓词转换的精度保真

Hive 谓词下推以 `SearchArgument` 形式到达，Hive 内部使用 `java.util.Date` 走默认时区且 Kryo 反序列化会丢微秒。`HiveIcebergFilterFactory` 通过反射读取 `PredicateLeafImpl` 的原始 `literal` 字段，再用 `LocalDateTime` 还原，避免时区与精度问题。这是与 Hive 序列化机制妥协的必要处理。

### 6.8 ObjectInspector 双重职责

Iceberg 自定义的 ObjectInspector 同时承担"读取呈现"（`getPrimitiveJavaObject`）与"写入转换"（`WriteObjectInspector.convert`）两种职责。通过 `WriteObjectInspector` 接口区分写入路径，若 OI 未实现该接口则写入时直接使用 Hive 原始对象。这让同一套 OI 既能服务于读也能服务于写。
