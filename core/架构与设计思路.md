# Iceberg `core` 模块架构与设计思路

> 本文基于 `core/src/main/java/org/apache/iceberg/` 源码（包根 `org.apache.iceberg`）整理，
> 描述 `iceberg-core` 模块在 Iceberg 整体架构中的层次定位、包结构、核心抽象、设计模式与关键流程。

## 1. 模块定位

`iceberg-core` 是 Iceberg 项目的**核心实现层**，负责把 `iceberg-api` 中定义的全部抽象接口落地为
可运行的实现，并补充表格式所需但 API 层未暴露的内部 SPI 与数据结构。它在 Iceberg 分层架构中
处于"承上启下"的关键位置：

- **向上**：实现 `api` 中的 `Table`、`Catalog`、`Scan`、`PendingUpdate`、`Action`、`FileIO`、
  `EncryptionManager`、`MetricsReporter` 等接口，让引擎模块（Spark/Flink/Hive/Trino）只需依赖
  `api` 即可面向接口编程，而把实现细节交给 `core`。
- **向下**：把"元数据文件存储在文件系统、元数据指针存储在 metastore"这一通用模式抽象为
  `TableOperations` SPI，让 Hive/JDBC/REST/Hadoop/In-Memory/Nessie 等后端只需实现少数抽象方法
  即可接入 Iceberg 生态。
- **格式实现**：内置 Avro 文件格式的完整读写实现（manifest 文件、metadata 文件均使用 Avro），
  并通过 `FileAppenderFactory` / `FileWriterFactory` 等 SPI 把 Parquet/ORC 等数据文件格式的
  实现下放到 `iceberg-parquet` / `iceberg-orc` 等子模块，避免 core 硬依赖具体格式。

`core` 模块本身不依赖任何计算引擎，但会依赖 Hadoop Common（用于 `HadoopFileIO`、`HadoopTableOperations`
等基于文件系统的实现）与 Caffeine 缓存、Jackson 等。

## 3. 核心类与设计模式

### 3.1 表与元数据核心

| 类/接口 | 设计意图 | 设计模式 |
| --- | --- | --- |
| `TableOperations`（[TableOperations.java](src/main/java/org/apache/iceberg/TableOperations.java)） | 表元数据访问与原子提交的 SPI；`commit(base, metadata)` 要求实现方保证原子性，状态未知时必须抛 `CommitStateUnknownException` 以便上层清理 | SPI + 乐观锁契约 |
| `TableMetadata`（[TableMetadata.java](src/main/java/org/apache/iceberg/TableMetadata.java)） | 表元数据不可变值模型，所有变更通过 `Builder` 生成新实例，支持快照懒加载与 `changes` 变更追踪 | Immutable Value Object + Builder |
| `BaseTable`（[BaseTable.java](src/main/java/org/apache/iceberg/BaseTable.java)） | `Table` 核心实现，把所有元数据查询委托给 `TableOperations.current()`，把所有更新工厂实例化为独立对象；`writeReplace()` 替换为 `SerializableTable` 跨进程传递 | Delegate + Serialization Proxy |
| `BaseMetastoreCatalog`（[BaseMetastoreCatalog.java](src/main/java/org/apache/iceberg/BaseMetastoreCatalog.java)） | 基于 metastore 的 Catalog 骨架，子类只需实现 `newTableOps` 与 `defaultWarehouseLocation`；统一处理普通表与元数据表标识符 | Template Method |
| `BaseMetastoreTableOperations`（[BaseMetastoreTableOperations.java](src/main/java/org/apache/iceberg/BaseMetastoreTableOperations.java)） | 基于 metastore 的 TableOperations 骨架，封装"元数据文件存 FS、指针存 metastore"模式；子类实现 `doRefresh`/`doCommit`；通过 `checkCommitStatus` 应对网络抖动 | Template Method + 乐观 CAS + 状态检查 |
| `CachingCatalog`（[CachingCatalog.java](src/main/java/org/apache/iceberg/CachingCatalog.java)） | Catalog 装饰器，Caffeine softValues + 可选过期；drop/rename 自动失效缓存条目并联动元数据表 | Decorator |
| `CatalogUtil`（[CatalogUtil.java](src/main/java/org/apache/iceberg/CatalogUtil.java)） | 反射加载 Catalog/FileIO/Reporter 的统一入口，通过 `Dyn*` 工具屏蔽跨版本/ClassLoader 差异 | Static Factory + Reflection |

### 3.2 快照提交体系（SnapshotProducer/MergingSnapshotProducer）

| 类/接口 | 设计意图 | 设计模式 |
| --- | --- | --- |
| `SnapshotProducer<ThisT>`（[SnapshotProducer.java](src/main/java/org/apache/iceberg/SnapshotProducer.java)） | 所有产生新快照的更新操作的抽象基类：管理 manifest 写入、manifest list 生成、CAS 重试、`stageOnly` 暂存、`toBranch` 分支提交、删除回调、指标上报；用 Caffeine 缓存 manifest 元数据补全 | Template Method + CRTP + Optimistic Retry |
| `MergingSnapshotProducer<ThisT>`（[MergingSnapshotProducer.java](src/main/java/org/apache/iceberg/MergingSnapshotProducer.java)） | 在 `SnapshotProducer` 之上增加 manifest 合并（`ManifestMergeManager`）与文件过滤（`ManifestFilterManager`）能力，是 `MergeAppend`/`BaseOverwriteFiles`/`BaseRowDelta`/`BaseReplacePartitions`/`StreamingDelete`/`BaseRewriteFiles` 的共同父类 | Template Method |
| `FastAppend`（[FastAppend.java](src/main/java/org/apache/iceberg/FastAppend.java)） | 快速追加，不合并 manifest，直接生成新 manifest 追加到 manifest list | Strategy（与 `MergeAppend` 相对） |
| `MergeAppend` | 合并追加，触发 manifest 合并以控制 manifest 数量 |
| `BaseOverwriteFiles` / `BaseRowDelta` / `BaseReplacePartitions` / `StreamingDelete` / `BaseRewriteFiles` / `BaseRewriteManifests` | 各类快照更新子类，复用 `MergingSnapshotProducer` 的合并/过滤骨架，定制各自的验证与 manifest 处理 |

## 4. 关键流程

### 4.1 加载表（Catalog.loadTable）

```
Catalog.loadTable(identifier)
  BaseMetastoreCatalog 实现：
  -> isValidIdentifier(identifier) ? newTableOps(identifier) : ...
  -> ops.current() != null
       ? new BaseTable(ops, fullTableName(...), metricsReporter)   // 普通表
       : isValidMetadataIdentifier(identifier)
           ? loadMetadataTable(identifier)                          // 元数据表（如 db.t.files）
           : throw NoSuchTableException
  // CachingCatalog 装饰：命中缓存则直接返回，否则委托底层 catalog 后缓存
```

`newTableOps` 由具体 Catalog 子类实现（Hive/JDBC/REST/Hadoop），返回的 `TableOperations` 负责从
底层存储加载 metadata 文件并解析为 `TableMetadata`。

### 4.2 创建表（Catalog.createTable）

```
Catalog.createTable(identifier, schema, spec, location, properties)
  默认实现：
  -> buildTable(identifier, schema)                                // BaseMetastoreCatalogTableBuilder
       .withPartitionSpec(spec).withLocation(location).withProperties(properties)
       .create()
  -> Builder.create():
       1. newTableOps(identifier)
       2. ops.current() != null -> throw AlreadyExistsException
       3. TableMetadata.newTableMetadata(schema, spec, sortOrder, location, properties)
       4. ops.commit(null, newMetadata)                            // 原子提交，写入 metastore
       5. return new BaseTable(ops, name, metricsReporter)
```

### 4.3 扫描规划（TableScan.planFiles / planTasks）

```
Table.newScan()  // -> DataTableScan
  .select(columns).filter(expr).caseSensitive(false)
  -> Scan 不可变，每次配置返回新实例

scan.planFiles():
  BaseTableScan.planFiles()
  -> 当前快照的 dataManifests + deleteManifests
  -> new ManifestGroup(io, dataManifests, deleteManifests)
       .specsById(specsById)
       .filterData(dataFilter)             // 数据过滤表达式
       .filterPartitions(partitionFilter)  // 分区过滤
       .filterManifests(manifestPredicate) // manifest 级过滤（ManifestEvaluator）
       .ignoreDeleted(ignoreDeleted)       // 跳过纯删除 manifest
       .project(columns)                   // 列投影
       .caseSensitive(caseSensitive)
       .planExecutor(executorService)      // 并行规划
       .scanMetrics(scanMetrics)
  -> ManifestGroup.planFiles()             // 产出 FileScanTask（含匹配的 DeleteFile）
       对每个 manifest：
         ManifestEvaluator 评估 manifest 是否可能命中  // manifest 级裁剪
         ManifestReader 读取 manifest 条目
         InclusiveMetricsEvaluator/StrictMetricsEvaluator  // 文件级裁剪（用 lower/upper bounds）
         DeleteFileIndex.forDataFile(...)  // 匹配删除文件
       产出 FileScanTask（dataFile + 对应 deleteFiles + 残留表达式）

scan.planTasks():
  BaseTableScan.planTasks()
  -> planFiles() -> TableScanUtil.splitFiles + combinePathInputSplits  // 切分大文件
  -> BinPacking.pack  // 合并小文件为均衡 CombinedScanTask
```

### 4.4 追加数据（AppendFiles.commit）

```
Table.newAppend()  // -> MergeAppend (会合并 manifest)
  .appendFile(dataFile)
  .appendManifest(manifestFile)
  .commit()

MergeAppend.commit() -> MergingSnapshotProducer.commit()
  SnapshotProducer.commit():
    OOP:
      attempt = 0
      loop:
        base = ops.current()                              // 最新基础元数据
        updated = apply(base)                             // 计算新元数据（含新快照）
        try:
          ops.commit(base, updated)                       // CAS 提交
          break
        catch CommitFailedException:
          if attempt++ < maxRetries: continue             // 重试
          else: throw
        catch CommitStateUnknownException:
          // 提交状态未知，不清理文件
          throw
      清理未提交的 manifest 文件（CleanableFailure 时）
      上报 CommitMetrics、触发 CreateSnapshotEvent

  MergingSnapshotProducer.apply(base):
    1. 写入新数据文件到新 manifest（RollingManifestWriter）
    2. ManifestFilterManager 过滤旧 manifest（删除规则、序列号清理）
    3. ManifestMergeManager 合并小 manifest（按 spec 分组）
    4. 生成 manifest list 文件
    5. 构造新 Snapshot + 更新 TableMetadata（addSnapshot, setSnapshotRef）
    6. 返回 updated TableMetadata
```

`FastAppend` 跳过步骤 2-3，直接追加新 manifest，适合小批量快速提交，代价是 manifest 数量增长。

### 4.5 事务提交（Transaction.commitTransaction）

```
Table.newTransaction()  // -> Transactions.newTransaction -> BaseTransaction(SIMPLE)

transaction.newAppend().appendFile(f).commit()   // 事务内 commit
  -> TransactionTableOperations.commit(base, metadata)
       仅更新内存 current（TransactionTableOperations），不真正落盘
  -> PendingUpdate 加入 updates 列表
  -> hasLastOpCommitted = true

transaction.newDelete().deleteFromRowFilter(...).commit()  // 再来一个操作

transaction.commitTransaction():
  BaseTransaction.commitTransaction():
    1. 检查 hasLastOpCommitted
    2. CAS 重试循环：
         base = ops.current()
         current = base
         for update in updates:
           current = update.applyUpdates(current, ...)    // 在最新 base 上重新应用全部变更
         ops.commit(base, current)                        // 一次性原子提交
    3. 失败则清理未提交文件，成功则清理被删除文件
```

事务的关键：各 `PendingUpdate` 的 `apply` 必须是幂等且可在任意 base 上重放的，以支持 CAS 重试时
重新应用全部变更。

### 4.6 快照过期（ExpireSnapshots）

```
Table.expireSnapshots()  // -> RemoveSnapshots

expire.expireOlderThan(ts).retainLast(n).commit()
  RemoveSnapshots.commit():
    1. apply(): 计算 toRemoveSnapshots（按年龄/数量/ref 年龄），更新 TableMetadata（RemoveSnapshots update）
    2. ops.commit(base, updated)                        // 先提交元数据（移除快照引用）
    3. cleanExpiredSnapshots():                          // 后清理文件（可重试）
         单 ref 默认 IncrementalFileCleanup（增量清理：只清理新过期快照独有的文件）
         多 ref 使用 ReachableFileCleanup（可达性清理：遍历所有仍可达文件，删除不可达的）
       清理对象：数据文件、manifest、manifest list、metadata 文件
```

两阶段设计保证元数据先行，文件清理可重试，即使清理失败也不影响表一致性。

### 4.7 Schema 演进（UpdateSchema.commit）

```
Table.updateSchema()  // -> SchemaUpdate

updateSchema.addColumn("new_col", Types.LongType.get()).renameColumn("a","b").commit()
  SchemaUpdate.commit():
    1. apply(): 由 ApplyChanges 访问者遍历现有 schema，应用 deletes/updates/adds/moves
                -> 产出新 Schema（新分配字段 ID，保留旧字段 ID）
    2. 更新 NameMapping（属性中的默认映射）
    3. ops.commit(base, base.updateSchema(newSchema, newLastColumnId))
```

字段 ID 是稳定标识：重命名只改 name 不改 ID，新增列分配新 ID，删除列保留 ID 不可复用。

### 4.8 REST Catalog 提交

```
RESTCatalog.loadTable / createTable / ...
  -> RESTSessionCatalog（持有 HTTPClient、auth、缓存）
  -> 通过 RESTClient 发起 HTTP 请求到 REST 服务端
  -> 服务端（CatalogHandlers）调用 BaseMetastoreCatalog 等本地实现
  -> 返回响应（含 metadata 文件位置或完整 TableMetadata）

RESTTableOperations.commit(base, metadata):
  -> POST /v1/{prefix}/namespaces/{ns}/tables/{tbl}/commit
     body: UpdateTableRequest(requirements + updates)
  -> 服务端校验 requirements（UpdateRequirement.validate）
  -> 服务端应用 updates（MetadataUpdate.applyTo）
  -> 服务端 CAS 提交
  -> 冲突返回 409，客户端重试
```

REST Catalog 把 `MetadataUpdate` + `UpdateRequirement` 模型序列化为 JSON 在客户端与服务端之间
传递，是"Requirement + Update"二元模型的典型应用场景。

## 6. 设计亮点与权衡

### 6.1 SPI 模板方法：TableOperations / BaseMetastoreCatalog / BaseMetastoreTableOperations

`core` 把"元数据文件存储在 FS、指针存储在 metastore"这一通用模式抽象为 `BaseMetastoreTableOperations`
模板方法，子类（Hive/JDBC/REST）只需实现 `doRefresh()` 和 `doCommit()` 两个钩子即可接入新的
metastore；`BaseMetastoreCatalog` 同理只需 `newTableOps` 与 `defaultWarehouseLocation`。

**亮点**：新增 metastore 后端的成本极低；通用流程（元数据文件读写、版本解析、提交状态检查、UUID 校验、
负缓存规避、重试）全部在基类统一维护。

**权衡**：基类承载了大量通用逻辑，子类必须理解基类的契约（如 `checkCommitStatus` 的调用时机、
`metadataFileLocation` 的约定），学习曲线较陡。

### 6.2 乐观并发 + CAS 重试 + 状态检查

`SnapshotProducer.commit` 与 `BaseTransaction.commitTransaction` 都采用 CAS 重试：先 `ops.current()`
拿到 base，`apply(base)` 计算新元数据，`ops.commit(base, updated)` 原子提交，冲突则刷新 base 重试。
`BaseMetastoreTableOperations` 进一步通过 `checkCommitStatus` 应对"提交实际成功但响应丢失"的
网络抖动场景。

**亮点**：无锁并发，多写入方互不阻塞；`CommitStateUnknownException` 明确区分"确定失败"与"状态未知"，
让上层正确决定是否清理文件。

**权衡**：重试时需重新 apply 全部变更（事务场景），要求 `PendingUpdate.apply` 幂等且可重放；
高冲突场景下重试开销可能显著。

### 6.3 Requirement + Update 二元模型

`MetadataUpdate`（变更命令）与 `UpdateRequirement`（前置条件）分离，是 Iceberg 提交协议的核心。
客户端把变更与期望状态打包发送（REST Catalog 场景），服务端先 `validate(requirements)` 再
`applyTo(updates)`，支持乐观锁重试。

**亮点**：变更可序列化、可审计、可重放；前置条件显式表达期望状态，避免 ABA 问题；同一份变更可在
不同 base 上重试提交。

**权衡**：模型较重，简单的属性更新也要包装成 Update 对象；但换来的是统一的提交协议与可重放性。

### 6.4 不可变值对象 + Builder + 懒加载

`TableMetadata`、`ViewMetadata`、`Schema`（api 层）、`BaseFile` 等核心元数据都是不可变值对象，
变更通过 Builder 生成新实例。派生视图（`snapshots`、`allManifests`、`addedDataFiles` 等）标记
`transient` 懒加载，部分用 `volatile` + 双检锁保证并发安全。

**亮点**：天然支持乐观并发（base 与 updated 互不影响）；序列化体积可控；冷启动开销低。

**权衡**：懒加载字段在反序列化后需重建，存在首次访问延迟；双检锁增加实现复杂度。

### 6.5 manifest 三层过滤 + 删除文件索引

扫描规划时，`ManifestGroup` 应用三层过滤：

1. **manifest 级**：`ManifestEvaluator` 用 manifest 的分区字段上下界裁剪整个 manifest。
2. **文件级**：`InclusiveMetricsEvaluator`（不漏）与 `StrictMetricsEvaluator`（不误删）用文件的
   列统计（lower/upper bounds、null/nan 计数）裁剪单个文件。
3. **删除文件匹配**：`DeleteFileIndex` 按 (specId, partition) 组织删除文件，按 apply_sequence_number
   排序，对每个数据文件二分查找需应用的删除文件集合，再用列统计过滤不可能匹配的删除文件。

**亮点**：分层裁剪大幅减少 IO；删除文件索引把"O(数据文件 × 删除文件)"的匹配降到接近 O(数据文件 + 删除文件)"。

**权衡**：过滤逻辑复杂，维护成本高；列统计依赖写入时正确收集，统计缺失时退化为全扫描。

### 6.6 装饰器与策略组合

`CachingCatalog` 装饰任意 Catalog 增加缓存；`ResolvingFileIO` 代理多种 FileIO 按 scheme 分派；
`MetricsReporters` 用 Composite 合并多个 reporter；`FileCleanupStrategy` 把过期清理分为
`IncrementalFileCleanup` 与 `ReachableFileCleanup` 两种策略。

**亮点**：能力可叠加，单一职责；新增策略不影响既有实现。

**权衡**：装饰器层级深时调试不便；策略选择逻辑分散在调用方。

### 6.7 写入器 SPI 下放格式实现

`FileAppenderFactory`/`FileWriterFactory` 把 Parquet/ORC 等格式特定的 writer 创建逻辑下放到
`iceberg-parquet`/`iceberg-orc` 子模块，`core` 只提供 `DataWriter`/`ClusteredWriter`/`FanoutWriter`
等不依赖具体格式的写入骨架。

**亮点**：core 不硬依赖具体文件格式，格式实现可独立演进；引擎按需引入格式模块。

**权衡**：写入器创建链条较长（Factory → RollingWriter → ClusteredWriter → DataWriter → FileAppender），
理解成本较高。

### 6.8 序列化代理与可序列化表视图

`BaseTable.writeReplace()` 替换为 `SerializableTable.copyOf(this)`，后者基于 `StaticTableOperations`
持有完整元数据快照，不再依赖 Catalog；`BaseMetadataTable.writeReplace()` 同理。`Schema`、`Type` 等
也通过 `writeReplace` 保持单例语义或控制序列化体积。

**亮点**：Spark 等引擎可把表对象序列化分发到 executor，无需在 executor 重建 Catalog 连接；
适合离线分析场景。

**权衡**：序列化后的表是只读快照，无法刷新；元数据较大时序列化体积可能显著（`SerializableTable`
做了字段裁剪优化）。

### 6.9 元数据表的统一抽象

`BaseMetadataTable` 把所有元数据表（`table.files`、`table.history`、`table.snapshots`、
`table.entries`、`table.partitions`、`table.refs` 等）统一为只读表视图，通过 `transformSpec`
把用户谓词改写为针对底层表 partition 列的过滤，复用扫描规划框架。

**亮点**：元数据表与普通表共享扫描/谓词下推/列裁剪等能力，引擎无需特殊处理；新增元数据表只需
继承 `BaseMetadataTable` 并定义 schema 与数据来源。

**权衡**：元数据表的 schema 是固定的（按 Iceberg 规范定义），扩展需谨慎考虑兼容性。

### 6.10 WAP（Write-Audit-Publish）与分支

`SnapshotUpdate.stageOnly()` 支持暂存快照但不切换当前快照 ID；`toBranch(branch)` 支持提交到
指定分支。配合 `SnapshotRef`（branch/tag）实现 WAP 工作流与表分支。

**亮点**：在表格式层面原生支持 WAP 与分支，无需额外基础设施；分支提交与主分支隔离，适合数据发布前审计。

**权衡**：暂存快照仍占用存储，需配合过期策略清理；分支语义增加了快照管理的复杂度。
