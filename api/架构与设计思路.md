# Iceberg `api` 模块架构与设计思路

> 本文基于 `api/src/main/java/org/apache/iceberg/` 源码（包根 `org.apache.iceberg`）整理，描述
> `iceberg-api` 模块在 Iceberg 整体架构中的层次定位、包结构、核心抽象、设计模式与关键流程。

## 1. 模块定位

`iceberg-api` 是 Iceberg 项目最顶层的**公共契约模块**，定义了 Iceberg 表格式对外暴露的全部
抽象接口与不可变数据结构，是 core 实现、各存储集成（Hadoop/JDBC/REST/In-Memory）、各引擎集成
（Spark/Flink/Hive/Trino）共同依赖的稳定基座。

- **职责边界**：只描述"做什么"，不规定"怎么做"。所有元数据更新、扫描、Catalog 操作在这里仅以
  接口形式存在；具体实现下沉到 `iceberg-core` 与各集成模块。
- **依赖方向**：`api` 不依赖 `core`，反向被 `core` 实现、被引擎模块消费，保证引擎只需依赖
  `api` 即可面向接口编程。
- **稳定性要求**：接口与字段 ID（如 `DataFile.FILE_PATH=100`、`ManifestFile.PATH=500`）一旦发布
  即视为表格式契约，跨版本兼容；新增能力通过 `default` 方法提供兜底实现，避免破坏既有实现。

在 Iceberg 三层表元数据（metadata file → manifest list → manifest → data file）模型中，`api`
模块负责定义 metadata file、manifest list、manifest 与 data file 各层对象的**契约接口**与
**字段 Schema 常量**，但不负责具体的 Avro/Parquet 读写实现。

## 3. 核心类与设计模式

### 3.1 表与元数据核心抽象

| 类/接口 | 设计意图 | 设计模式 |
| --- | --- | --- |
| `Table`（[Table.java](src/main/java/org/apache/iceberg/Table.java)） | 表的统一契约：暴露 schema/spec/sortOrder/snapshot 等元数据查询与 `newScan`、`newAppend`、`newOverwrite`、`updateSchema` 等更新入口；默认方法为可选能力提供兜底（如 `newBatchScan` 通过 `BatchScanAdapter` 适配） | 接口隔离 + 默认方法适配 |
| `Transaction`（[Transaction.java](src/main/java/org/apache/iceberg/Transaction.java)） | 把多个表更新打包为一次原子提交；内部维护暂存表视图，提交时统一应用到最新元数据 | Unit of Work / 暂存视图 |
| `Schema`（[Schema.java](src/main/java/org/apache/iceberg/Schema.java)） | 描述表列结构，采用**字段 ID**（而非列名）作为稳定标识，支持列重命名/重排演进；各类索引（idToField、nameToId 等）以 `transient` + 懒加载持有，避免序列化膨胀 | 不可变值对象 + 懒加载 |
| `PartitionSpec`（[PartitionSpec.java](src/main/java/org/apache/iceberg/PartitionSpec.java)） | 描述分区字段（源字段 + Transform）集合，分区字段 ID 从 1000 起分配、跨 spec 共享 ID 空间；派生视图（partitionType、javaClasses 等）以 `transient volatile` + 双检锁懒加载 | 不可变值对象 + 双检锁 |
| `SortOrder`（[SortOrder.java](src/main/java/org/apache/iceberg/SortOrder.java)） | 描述表排序顺序，由 `SortField`（字段 + Transform + 方向 + null 顺序）组成 |
| `Snapshot`（[Snapshot.java](src/main/java/org/apache/iceberg/Snapshot.java)） | 表在某一时刻的数据状态，由 manifest list 引用，通过 parentId 形成快照链，支持时间旅行；实现 `Serializable` | 不可变快照 |
| `ManifestFile`（[ManifestFile.java](src/main/java/org/apache/iceberg/ManifestFile.java)） | manifest 文件元信息接口，固定字段 ID（500~519）持久化，是三层元数据的中间层 |
| `DataFile` / `DeleteFile` / `ContentFile` | 数据/删除文件元数据，固定字段 ID（100+）保证 manifest 文件格式跨版本稳定 |

### 3.2 更新 API 体系（PendingUpdate/SnapshotUpdate）

### 3.3 扫描 API 体系

## 4. 关键流程

### 4.1 加载表

```
Catalog.loadTable(identifier)
  -> Catalog 实现读取 catalog 后端（HMS/JDBC/REST/Hadoop 文件系统）
  -> 定位 metadata 文件位置
  -> 由 core 模块 TableOperations 解析 metadata JSON
  -> 返回实现 Table 接口的对象（如 BaseTable / RESTTable）
```

`api` 层只定义 `Catalog.loadTable` 与 `Table` 契约，具体解析与构造在 core。

### 4.2 创建表

```
Catalog.createTable(identifier, schema, spec, location, properties)
  默认实现：
  -> buildTable(identifier, schema)
       .withPartitionSpec(spec)
       .withLocation(location)
       .withProperties(properties)
       .create()
```

`Catalog` 通过 `TableBuilder` 把多种创建变体（带/不带 location、带/不带属性）收敛到统一构建器，
避免长参数列表；`TableBuilder` 同时支持 `createTransaction` / `replaceTransaction` /
`createOrReplaceTransaction`，复用同一构建器开启事务。

### 4.3 扫描规划（不可变链式配置）

```
Table.newScan()
  .select(columns)        // 返回新 Scan 实例（投影）
  .filter(expression)     // 返回新 Scan 实例（过滤）
  .caseSensitive(false)   // 返回新 Scan 实例
  .planFiles()            // 产出整文件 ScanTask 迭代器
  .planTasks()            // 产出切分/合并后的均衡 ScanTaskGroup 迭代器
```

`Scan` 的所有配置方法都返回新实例，便于在多线程间共享与缓存；`api` 仅定义契约，
`planFiles`/`planTasks` 的具体规划逻辑（manifest 过滤、分区裁剪、文件切分合并）在 core 实现。

### 4.4 元数据更新（两阶段提交）

```
PendingUpdate<T>
  apply()   // 计算待提交变更（不持久化），返回变更对象供校验
  commit()  // 通过底层 TableOperations 原子提交
```

- 产生快照的更新（`AppendFiles`/`OverwriteFiles`/`RewriteFiles` 等）继承 `SnapshotUpdate`，
  支持自定义 summary、删除回调、`stageOnly` 暂存、`toBranch` 分支提交。
- 不产生快照的演进（`UpdateSchema`/`UpdatePartitionSpec`/`UpdateProperties` 等）直接继承 `PendingUpdate`。
- `Transaction` 把多个 `PendingUpdate` 在暂存视图上累积，`commitTransaction()` 时一次性应用到最新元数据，
  冲突抛 `CommitFailedException`。

### 4.5 表达式绑定与求值

```
Expressions.and(Expressions.lessThan("id", 100), Expressions.notNull("name"))   // 未绑定
  -> Binder.bind(schema, expr, caseSensitive)                                    // 绑定到字段 ID
  -> Evaluator / InclusiveMetricsEvaluator / StrictMetricsEvaluator             // 求值/文件过滤
  -> Projections.project(spec, expr)                                             // 投影到分区值
  -> Transform.project(name, boundPredicate)                                     // inclusive/strict 投影
```

`api` 层提供完整的表达式构造、绑定、求值、投影契约；`Expressions` 工厂在构造期做常量折叠，
`Transform.project`（inclusive，不漏数据）与 `Transform.projectStrict`（strict，可整体跳过文件）
共同构成完整的过滤边界。

## 5. 与其他模块的关系

### 5.1 依赖的模块

`api` 模块依赖极为精简：

- `iceberg-bundled-guava`（relocated `org.apache.iceberg.relocated.com.google.common.*`）：避免与
  引擎自带 Guava 版本冲突。
- `org.slf4j`：日志门面。
- `org.apache.avro`（仅用于 `Schema` 与 Avro 的少量互转常量，可视为可选）。

不依赖 `core`、不依赖任何引擎或存储 SDK，保证可作为最薄契约层被广泛复用。

### 5.2 被哪些模块依赖

- **`iceberg-core`**：实现 `api` 中几乎所有接口（`BaseTable`、`TableOperations`、`SnapshotProducer`、
  `MergingSnapshotProducer`、`BaseMetastoreCatalog`、各 `Base*` 扫描与更新类、各 metadata 表等）。
- **`iceberg-hadoop` / `iceberg-aws` / `iceberg-gcp` / `iceberg-azure` / `iceberg-jdbc` / `iceberg-rest`
  等存储集成**：实现 `FileIO`、`Catalog`。
- **`iceberg-spark*` / `iceberg-flink*` / `iceberg-hive` / `iceberg-trino` 等引擎集成**：面向
  `api` 接口编程，把引擎的 plan/optimize/write 转译为 `Scan`/`PendingUpdate`/`Action` 调用。
- **`iceberg-data` / `iceberg-parquet` / `iceberg-orc` / `iceberg-avro`**：基于 `DataFile`、
  `FileIO`、`Schema`、`Type` 等实现读写器。

## 6. 设计亮点与权衡

### 6.1 接口先行 + 默认方法编排

`Catalog`、`Table`、`Scan` 等顶层接口大量使用 Java 8 默认方法：

- 把"通用编排"（如 `createTable` 委托 `buildTable`、`tableExists` 委托 `loadTable` 捕获异常、
  `newBatchScan` 通过 `BatchScanAdapter` 适配）放在接口默认方法中，减少实现类样板代码。
- 可选能力（`updateStatistics`、`newIncrementalAppendScan`、`toBranch`、`metricsReporter`）默认抛
  `UnsupportedOperationException`，由具体实现按需覆盖，避免接口膨胀同时保证调用方尽早暴露错误。

**权衡**：默认方法让接口演进更平滑，但也意味着实现类若忘记覆盖，错误会延迟到运行时才暴露。

### 6.2 字段 ID 作为稳定标识

`Schema`、`DataFile`、`ManifestFile`、`ManifestEntry` 等都以**固定字段 ID**持久化（如
`DataFile.FILE_PATH=100`、`ManifestFile.PATH=500`），而非列名或位置。这是 Iceberg 表格式
支持列重命名/重排/删除演进的根本机制，也是 `api` 模块作为格式契约层的核心约束。

**权衡**：新增字段时必须按 `NEXT ID TO ASSIGN` 顺序分配，且 ID 一旦分配不可复用，管理成本较高。

### 6.3 不可变值对象 + 懒加载视图

`Schema`、`PartitionSpec`、`SortOrder` 等把"持久化必需字段"作为 `final` 字段，把"派生视图"
（idToField、partitionType、javaClasses 等）作为 `transient` + 懒加载持有，部分还使用
`volatile` + 双检锁保证并发安全。这样既控制了序列化体积（避免 Spark 等引擎分发时膨胀），
又支持首次访问时构建、冷启动开销低。

**权衡**：懒加载字段在反序列化后需重建，存在首次访问延迟；双检锁也增加了实现复杂度。

### 6.4 不可变扫描 + 链式配置

`Scan` 所有配置方法返回新实例，扫描对象一旦创建即不可变、线程安全。这便于在多线程间共享与缓存，
也契合 Spark/Flink 等 Catalyst/Optimizer 阶段反复变换扫描配置的模式。

**权衡**：每次配置变更都新建对象，存在一定分配开销；但扫描配置阶段非热路径，可接受。

### 6.5 两阶段提交支撑乐观并发

`PendingUpdate.apply()` / `commit()` 把"计算变更"与"提交变更"分离，配合 core 层的
`TableOperations.commit` 基于 metadata 文件指针的乐观锁，实现多写入方冲突重试。
`SnapshotUpdate.stageOnly()` 进一步支持 WAP（Write-Audit-Publish）场景。

**权衡**：调用方需理解两阶段语义，且 `apply` 后 `commit` 前表可能已前进，需要重试逻辑兜底
（core 实现）。

### 6.6 能力混合接口（Interface Segregation）

`SupportsNamespaces`、`ViewCatalog`、`SessionCatalog`、`SupportsBulkOperations`、
`SupportsPrefixOperations` 等以独立接口声明可选能力，Catalog/FileIO 通过实现这些接口表明
支持相应能力，避免在主接口堆砌方法。上层引擎通过 `instanceof` 判断并调用。

**权衡**：能力发现需 `instanceof` 检查，调用方代码略繁琐，但接口职责清晰、可演进。

### 6.7 表达式与变换的双向投影

`Transform.project`（inclusive，保证不漏数据）与 `Transform.projectStrict`（strict，保证不误删数据）
共同构成完整的分区裁剪边界：inclusive 用于挑选候选分区，strict 用于整体跳过文件内容过滤。
`Operation.negate`/`flipLR` 集中定义逻辑等价变换，使表达式改写不散落到各子类。

**权衡**：双向投影增加了变换实现的工作量（每个 Transform 都要实现两个 project），但保证了
过滤正确性边界清晰。

### 6.8 序列化友好

`FileIO`、`EncryptionManager`、`Expression`、`Schema`、`Type` 等核心对象都实现 `Serializable`
或提供 `writeReplace` 代理（如 `PrimitiveType` → `PrimitiveHolder`），以支持 Spark 等引擎
把对象序列化分发到 executor 执行。`Schema` 的索引字段标记为 `transient` 也是为控制序列化体积。

**权衡**：序列化友好约束了字段类型必须可序列化，部分场景需借助 `SerializableSupplier`/
`SerializableFunction` 等包装。
