# iceberg-nessie 模块架构与设计思路

> 源码根目录：`nessie/src/main/java/org/apache/iceberg/nessie/`

## 1. 模块定位

`iceberg-nessie` 是 Iceberg 与 [Nessie](https://projectnessie.org/)（数据湖目录与版本控制服务）集成的 Catalog 模块，处于 Iceberg `api/core` 之上、Spark/Flink 等计算引擎之下。Nessie 提供 Git 风格的"数据湖版本控制"能力——通过分支（Branch）/标签（Tag）对数据湖元数据进行提交、隔离与回溯，使 Iceberg 表能够支持跨分支的并发开发、时间旅行（time travel）与多环境隔离。

与 `iceberg-aws` 同时承担 Catalog 与 FileIO 两类职责不同，`iceberg-nessie` 聚焦于**元数据目录（Catalog）**这一单一职责：

- 把 Nessie 的 `ContentKey`（命名空间 + 表名）、`IcebergTable`（Nessie 中对 Iceberg 表元数据的封装）、`Reference`（分支/标签）模型映射为 Iceberg 的 `TableIdentifier`、`TableMetadata`、`TableOperations`。
- 把表元数据 commit 操作翻译为 Nessie 的 `commitMultipleOperations`（Put/Delete Content + CommitMeta），借助 Nessie 服务端的乐观并发控制（expectedHead hash）保证原子性。
- 底层数据与元数据文件的物理存储通过可插拔的 `FileIO`（默认 `HadoopFileIO`）承担，与 Nessie 服务本身解耦。

模块的显著特征是**引用感知（reference-aware）**：每次表操作可绑定一个 Nessie 分支或标签及其特定 hash，从而在同一 Catalog 实例下访问不同版本的数据。

## 2. 包结构概览

`iceberg-nessie` 模块非常精简，所有类直接位于 `org.apache.iceberg.nessie` 包下，无子包划分：

```
org.apache.iceberg.nessie
├── NessieCatalog          Catalog 入口，实现 BaseMetastoreCatalog + SupportsNamespaces
├── NessieIcebergClient    Nessie API 客户端封装，承载所有与服务端的交互逻辑
├── NessieTableOperations  单表的 TableOperations 实现
├── NessieUtil             工具类：ContentKey 转换、提交元数据构建、GC 检查等
└── UpdateableReference    对 Nessie Reference 的可更新包装，管理可变性与刷新
```

| 类 | 职责 |
| --- | --- |
| `NessieCatalog` | Iceberg Catalog 入口。负责初始化 Nessie 客户端与 FileIO、解析引用、表/命名空间的增删改查与重命名、warehouse 路径推导。 |
| `NessieIcebergClient` | Nessie `NessieApiV1` 的封装。管理 `UpdateableReference`，提供表列举、加载、commit、命名空间 CRUD 等，并实现 `withReference` 派生客户端。 |
| `NessieTableOperations` | 单表元数据操作实现。`doRefresh` 从 Nessie 读取 `IcebergTable` 的 `metadataLocation` 并加载元数据；`doCommit` 委托 `NessieIcebergClient.commitTable`。 |
| `NessieUtil` | 静态工具：`TableIdentifier`↔`ContentKey` 转换、`CommitMeta` 构建（author/properties）、GC 属性检查与警告、把 Nessie commit id 注入 `TableMetadata`。 |
| `UpdateableReference` | 对 `Reference` 的可变包装。区分可变（Branch 且未固定 hash）与不可变（Tag 或固定 hash），提供 `refresh`/`updateReference`/`checkMutable`。 |

## 3. 核心类与设计模式

### 3.1 NessieCatalog（Catalog 入口 + 引用解析 + 委托）

`NessieCatalog` 继承 `BaseMetastoreCatalog`，实现 `SupportsNamespaces` 与 `Configurable<Object>`。核心设计：

- **双初始化路径**：
  - `initialize(String, Map)`：标准反射加载入口。从 properties 读取 `nessie.ref`/`nessie.ref.hash`、API 版本（v1/v2）、FileIO 实现类，通过 `NessieClientBuilder.createClientBuilderFromSystemSettings` 构造 Nessie API，再委托给包级 `initialize`。
  - `initialize(String, NessieIcebergClient, FileIO, Map)`：供测试或预配置场景直接注入 client 与 FileIO。

- **引用解析**：`newTableOps` 通过 `parseTableReference` 解析表名中可能内嵌的 `branch@hash`/`tag@hash` 语法（基于 Nessie `TableReference.parse`），再用 `client.withReference(ref, hash)` 派生绑定特定引用的客户端。这使同一 Catalog 可同时操作不同分支的表。

- **warehouse 路径推导**：`defaultWarehouseLocation` 优先使用命名空间的 `location` 属性，否则用 `warehouse/namespace/table`；并在路径末尾追加 `_<UUID>`，避免不同分支下同名表共享物理路径导致数据冲突。

- **默认禁用 GC**：`DEFAULT_CATALOG_OPTIONS` 强制 `gc-enabled=false` 与 `metadata-delete-after-commit-enabled=false`，防止 Iceberg 的单分支 GC 误删其他分支/标签仍引用的文件，引导用户使用 Nessie 的引用感知 GC 工具 `nessie-gc`。

- **委托模式**：表/命名空间的 CRUD 几乎全部委托给 `NessieIcebergClient`，Catalog 本身只做引用解析与标识符转换。

### 3.2 NessieIcebergClient（服务端交互 + 引用管理 + 重试协调）

这是模块的核心引擎类，封装所有与 Nessie 服务端的交互。关键设计：

- **延迟加载引用**：构造时用 `Suppliers.memoize(() -> loadReference(requestedRef, requestedHash))` 延迟加载 `UpdateableReference`，首次调用 `getRef()` 时才发请求。`loadReference` 处理默认分支回退、hash 固定（Branch→`Branch.of`、Tag→`Tag.of`）、引用不存在时的友好错误。

- **引用派生**：`withReference(ref, hash)` 在引用与当前一致时返回 `this`（避免无谓创建），否则 new 一个新 client。这使不同表操作可绑定不同引用而互不干扰。

- **commit 模型**：`commitTable` 是核心。它从 `base` 元数据中取出 `nessie.commit.id`（上次加载时的 Nessie commit hash）作为 `expectedHead`，构造 `IcebergTable`（含 snapshotId/schemaId/specId/sortOrderId/metadataLocation），通过 `commitMultipleOperations().operation(Put.of(key, newTable, expectedContent)).branch(expectedHead).commit()` 提交。Nessie 服务端用 expectedHead hash 做乐观并发控制——若已被他人提交则返回 `NessieConflictException`。

- **重试与刷新**：`dropTable`/`renameTable` 用 `Tasks.foreach().retry(5).stopRetryOn(NessieNotFoundException.class).onFailure((o,e) -> refresh())` 模式，冲突时刷新本地引用再重试。`commitTable` 本身不重试，而是抛 `CommitFailedException` 由上层 Iceberg 决定是否重试。

- **异常映射**：`NessieConflictException`→`CommitFailedException`；`NessieNotFoundException`→`RuntimeException`（引用失效）；`HttpClientException`→`CommitStateUnknownException`（网络错误，提交状态未知）。

- **提交元数据**：通过 `NessieUtil.buildCommitData` 构建 `CommitMeta`，包含 commit message、author（`user` 配置或 `user.name` 系统属性）、`application-type=iceberg`、`app-id` 等，便于审计。

- **`withReference(builder)`**：内部辅助方法，根据引用可变性选择 `refName` 或 `reference`，统一处理读写请求的引用绑定。

### 3.3 NessieTableOperations（表元数据操作 + 冲突细化）

继承 `BaseMetastoreTableOperations`，实现单表 refresh/commit：

- **doRefresh**：
  1. `client.refresh()` 刷新本地引用到 Nessie 最新状态。
  2. `getContent().key(key).reference(reference).get()` 读取表 Content。
  3. Content 为 null 且本地已有元数据 → `NoSuchTableException`；为 null 且无本地元数据 → 空表。
  4. Content 非 IcebergTable → `IllegalStateException`。
  5. `refreshFromMetadataLocation(metadataLocation, null, 2, location -> ...)`：加载元数据文件，并通过 `NessieUtil.updateTableMetadataWithNessieSpecificProperties` 注入 Nessie 特有属性（commit id、GC 检查、snapshot/schema/spec/sortOrder 同步）。

- **doCommit**：
  1. `writeNewMetadataIfRequired` 写新元数据 JSON 到 FileIO。
  2. 委托 `client.commitTable(base, metadata, newMetadataLocation, table, key)`。
  3. `NessieConflictException` 中若是 `NessieReferenceConflictException`，调用 `maybeThrowSpecializedException` 根据 Nessie 返回的 `ReferenceConflicts` 细化为 `NoSuchNamespaceException`/`NamespaceNotEmptyException`/`NoSuchTableException`/`AlreadyExistsException`。
  4. 失败时 `io().deleteFile(newMetadataLocation)` 清理未提交的元数据文件。

- **Nessie commit id 同步**：`NESSIE_COMMIT_ID_PROPERTY` 是 TableMetadata 的属性，记录加载时的 Nessie commit hash。下次 commit 时作为 expectedHead，实现"读时版本→写时校验"的乐观锁链路。

### 3.4 UpdateableReference（可变引用包装）

对 Nessie `Reference` 的薄封装，核心是区分可变与不可变：

- **可变性判定**：`reference instanceof Branch && !hashReference`。即只有未固定 hash 的 Branch 才可写；Tag 或固定 hash 的 Branch 只读。
- **`checkMutable()`**：所有写操作前调用，对只读引用抛 `IllegalArgumentException`。
- **`refresh(api)`**：重新从服务端拉取引用最新状态，返回是否发生变化。
- **`updateReference(ref)`**：commit 成功后用服务端返回的新 Branch 更新本地状态。

**设计模式**：值对象 + 状态保护，把"引用可变性"这一不变式集中管理，避免散落在各业务方法中。

### 3.5 NessieUtil（工具集合）

静态工具类，承担：

- **标识符转换**：`toKey(TableIdentifier)` 把 Iceberg 标识符转为 Nessie `ContentKey`；`removeCatalogName` 在 rename 时剥离冗余的 catalog 名前缀。
- **提交元数据构建**：`buildCommitData`/`catalogOptions` 构造 `CommitMeta`，注入 author、`application-type=iceberg`、`app-id`。
- **元数据属性同步**：`updateTableMetadataWithNessieSpecificProperties` 把 Nessie 的 `IcebergTable`（snapshotId/schemaId/specId/sortOrderId）与 commit hash 同步回 `TableMetadata`，保证 Iceberg 视角与 Nessie 视角一致；同时调用 `checkAndUpdateGCProperties` 检查并警告不安全的 GC 配置。
- **GC 安全检查**：若表开启了 `gc-enabled` 或 `metadata-delete-after-commit-enabled`，记录警告并设置 `nessie.gc.no-warning`，引导用户使用 `nessie-gc` 工具做引用感知 GC，避免误删跨分支共享文件。

## 4. 关键流程

### 4.1 Catalog 初始化流程

```
NessieCatalog.initialize(name, options)
  ├─ 读取 fileIOImpl（默认 HadoopFileIO）
  ├─ 读取 nessie.ref / nessie.ref.hash
  ├─ 构造 NessieClientConfigSource（mapConfigSource + fallback 去 nessie. 前缀）
  ├─ NessieClientBuilder.createClientBuilderFromSystemSettings(configSource)
  ├─ 按 nessie.client-api-version 选择 NessieApiV1 / NessieApiV2
  ├─ new NessieIcebergClient(api, requestedRef, requestedHash, catalogOptions)
  ├─ CatalogUtil.loadFileIO(fileIOImpl, options, config)
  └─ initialize(name, client, fileIO, catalogOptions)
       ├─ 合并 DEFAULT_CATALOG_OPTIONS（禁用 GC）
       ├─ validateWarehouseLocation（warehouse 必填）
       └─ CloseableGroup 注册 client + fileIO 统一关闭
```

### 4.2 表加载与元数据读取流程（doRefresh）

```
NessieTableOperations.doRefresh()
  ├─ client.refresh()  ← 刷新本地引用到 Nessie 最新
  ├─ reference = client.getRef().getReference()
  ├─ client.getApi().getContent().key(key).reference(reference).get()
  │    └─ Content content = response.get(key)
  ├─ content == null:
  │    ├─ 本地有元数据 → throw NoSuchTableException
  │    └─ 本地无元数据 → 空表（metadataLocation=null）
  ├─ content.unwrap(IcebergTable)  ← 非 Iceberg 表抛异常
  └─ refreshFromMetadataLocation(metadataLocation, null, 2, location ->
       NessieUtil.updateTableMetadataWithNessieSpecificProperties(
         TableMetadataParser.read(fileIO, location), location, table, key, reference))
         ├─ 注入 nessie.commit.id = reference.getHash()
         ├─ checkAndUpdateGCProperties（GC 警告）
         ├─ 同步 snapshotId/schemaId/specId/sortOrderId
         └─ discardChanges().build()
```

### 4.3 表提交流程（doCommit）

```
NessieTableOperations.doCommit(base, metadata)
  ├─ writeNewMetadataIfRequired(newTable, metadata) → newMetadataLocation
  ├─ client.commitTable(base, metadata, newMetadataLocation, table, key):
  │    ├─ updateableReference.checkMutable()  ← Tag/固定hash 抛异常
  │    ├─ expectedHead = base 的 nessie.commit.id 或当前 Branch hash
  │    ├─ 构造 ImmutableIcebergTable(snapshotId, schemaId, specId, sortOrderId, metadataLocation)
  │    ├─ commitMultipleOperations()
  │    │    .operation(Operation.Put.of(key, newTable, expectedContent))
  │    │    .commitMeta(buildCommitMsg + author + application-type=iceberg)
  │    │    .branch(expectedHead)  ← 乐观锁：expectedHead 必须匹配
  │    │    .commit()
  │    │    └─ 返回新 Branch（含新 hash）
  │    └─ updateableReference.updateReference(newBranch)
  ├─ 异常处理:
  │    ├─ NessieConflictException:
  │    │    ├─ NessieReferenceConflictException → maybeThrowSpecializedException
  │    │    │    └─ 按 ReferenceConflicts 映射为 NoSuchNamespace/NamespaceNotEmpty/NoSuchTable/AlreadyExists
  │    │    └─ 其他 → CommitFailedException（引用过期，需刷新重试）
  │    ├─ HttpClientException → CommitStateUnknownException（网络错误，状态未知）
  │    └─ NessieNotFoundException → RuntimeException（引用不存在）
  └─ finally: 失败时 io().deleteFile(newMetadataLocation)
```

### 4.4 表列举与命名空间操作

```
NessieIcebergClient.listTables(namespace)
  └─ withReference(api.getEntries()).get()
       └─ entries.stream()
            .filter(namespacePredicate(namespace))  ← 前缀匹配命名空间层级
            .filter(e -> e.getType() == ICEBERG_TABLE)
            .map(this::toIdentifier)  ← ContentKey.elements → TableIdentifier
```

命名空间操作（create/list/drop/loadMetadata/setProperties/removeProperties）直接调用 Nessie API 的 `createNamespace`/`getMultipleNamespaces`/`deleteNamespace`/`getNamespace`/`updateProperties`，并通过 `withReference` 绑定引用、`refresh` 在可变引用上提交后刷新。

### 4.5 表重命名流程

```
NessieIcebergClient.renameTable(from, to)
  ├─ getRef().checkMutable()
  ├─ table(from) 校验源表存在（否则 NoSuchTableException）
  ├─ table(to) 校验目标表不存在（否则 AlreadyExistsException）
  ├─ commitMultipleOperations()
  │    .commitMeta("Iceberg rename table from ... to ...")
  │    .operation(Operation.Delete.of(toKey(from)))
  │    .operation(Operation.Put.of(toKey(to), existingFromTable))
  │    .branch((Branch) getRef().getReference()).commit()
  └─ Tasks.retry(5).onFailure(refresh)  ← 冲突时刷新引用重试
```

要点：重命名通过 Delete + Put 两个 Operation 在单次 commit 中完成，Nessie 保证原子性。

## 6. 设计亮点与权衡

### 6.1 引用感知的 Catalog 设计

`NessieCatalog.newTableOps` 解析表名内嵌的 `branch@hash`/`tag@hash`，通过 `client.withReference` 派生绑定引用的客户端，使同一 Catalog 实例可同时访问不同分支/标签的表。这是 Nessie 相对其他 Catalog 的核心差异——支持 Git 风格的数据湖分支开发与时间旅行。代价是引入 `TableReference` 解析与 `withReference` 派生开销，且 rename 强制要求 from/to 同引用。

### 6.2 乐观并发控制基于 commit hash

表 commit 以 `base` 元数据中的 `nessie.commit.id` 作为 `expectedHead` 提交给 Nessie，服务端校验 hash 匹配后才接受。这把"读时版本→写时校验"的乐观锁链路从 Iceberg 元数据文件延伸到 Nessie commit，无需额外锁组件。代价是冲突时需刷新引用并重试，`commitTable` 本身不重试而由上层决定。

### 6.3 引用可变性的集中管理

`UpdateableReference` 把"是否可写"（Branch 且未固定 hash）这一不变式集中管理，所有写操作前 `checkMutable`。Tag 与固定 hash 的 Branch 天然只读，支持时间旅行场景下的安全读取。代价是用户在只读引用上误操作时会得到明确错误而非静默失败。

### 6.4 默认禁用 GC 保护跨分支数据

Nessie 多分支场景下，文件可能被多个分支/标签引用。Iceberg 的单分支 GC（`expire_snapshots`/`remove_orphan_files`/`drop_table purge`）会误删其他分支仍需的文件。模块通过 `DEFAULT_CATALOG_OPTIONS` 强制 `gc-enabled=false`，并在 `checkAndUpdateGCProperties` 中对强行开启 GC 的表记录警告，引导使用 `nessie-gc` 做引用感知 GC。代价是用户需额外部署 `nessie-gc` 工具。

### 6.5 warehouse 路径追加 UUID 防冲突

不同分支下可能存在同名表，若共享物理路径会导致数据覆盖。`defaultWarehouseLocation` 在路径末尾追加 `_<UUID>`，保证每张表物理隔离。代价是路径不可预测，不利于人工定位文件。

### 6.6 冲突异常的细化映射

Nessie 服务端在 `NessieReferenceConflictException` 中返回 `ReferenceConflicts` 详情，`maybeThrowSpecializedException` 据此把通用冲突细化为 `NoSuchNamespaceException`/`NamespaceNotEmptyException`/`NoSuchTableException`/`AlreadyExistsException`，让上层引擎能展示更准确的错误。仅当只有一个 conflict 时才细化，避免歧义。

### 6.7 延迟加载与 memoize 优化

`NessieIcebergClient` 用 `Suppliers.memoize` 延迟加载 `UpdateableReference`，避免构造期即发请求；`withReference` 在引用一致时返回 `this` 避免无谓创建。代价是 `UpdateableReference` 的状态变更需通过 `refresh`/`updateReference` 显式同步。

### 6.8 FileIO 与 Catalog 解耦

Nessie 只负责元数据版本控制，物理文件存储完全交给可插拔 FileIO（默认 HadoopFileIO，可配 S3FileIO/GCSFileIO 等）。这使得 Nessie 可与任意对象存储/文件系统组合，不绑定特定云厂商。代价是 FileIO 配置需独立维护，且 GC 责任从 Catalog 转移到 `nessie-gc` 工具。

### 6.9 双 API 版本兼容

通过 `nessie.client-api-version` 配置选择 `NessieApiV1` 或 `NessieApiV2`，用 `NessieClientBuilder.build(Class)` 构造对应 API 实例。这使模块同时兼容 Nessie 的两个 API 版本，平滑过渡。代价是部分 v2 特有能力（如批量操作）在 v1 下不可用。

### 6.10 网络错误映射为 CommitStateUnknown

`HttpClientException`（含连接重置、超时等）被映射为 `CommitStateUnknownException` 而非 `CommitFailedException`，因为请求可能已到达服务端但响应丢失，提交状态无法确定。这避免上层误判为失败而重试导致重复提交。代价是上层需处理未知态，通常通过再次 refresh 确认。
