# Iceberg Spark 模块架构与设计思路

> 本文基于 `spark/v3.5` 子模块（含 `spark` 与 `spark-extensions`）源码梳理，并对照 `v3.2/v3.3/v3.4/v4.1` 的版本差异，总结 Iceberg 与 Apache Spark 集成层的整体架构、核心抽象与设计权衡。

---

## 1. 模块定位

Iceberg 整体架构分为三层：**核心 API 层**（`iceberg-api`/`iceberg-core`/`iceberg-data` 等通用表与扫描抽象）、**引擎集成层**（`spark`/`flink`/`mr`/`hive`/`nessie` 等）、**底层 IO 与文件格式层**（`parquet`/`orc`/`avro`/`arrow` 等）。

`spark` 模块处于 **引擎集成层**，承担以下职责：

- 将 Iceberg `Catalog`/`Table`/`TableScan`/`AppendFiles` 等核心抽象适配为 Spark DataSource V2 的 `TableCatalog`、`Table`、`Scan`、`BatchWrite`、`MicroBatchStream`、`RowLevelOperation` 等接口。
- 在 Spark Catalyst 中扩展 SQL 语法（`CALL` 存储过程、`ALTER TABLE ... ADD PARTITION FIELD`、`CREATE BRANCH`/`CREATE TAG` 等）。
- 把 Iceberg 的元数据能力（time travel、分支/标签、changelog、metadata columns、row-level operations）暴露为 Spark SQL 可见的能力。
- 借助 Spark 的分布式执行引擎实现 Iceberg 表维护操作（`RewriteDataFiles`、`ExpireSnapshots`、`MigrateTable`、`SnapshotTable` 等 Actions）。

简言之，`spark` 模块是 Spark 用户操作 Iceberg 表的「门面与适配器」，使得 Spark SQL、DataFrame、Structured Streaming 都能透明地读写、维护 Iceberg 表。

## 2. 多版本结构说明

### 2.1 顶层结构

```
spark/
├── build.gradle          # 顶层入口：按 sparkVersions 系统属性激活各版本
├── build/                # 顶层构建产物
├── v3.2/                 # Spark 3.2
├── v3.3/                 # Spark 3.3
├── v3.4/                 # Spark 3.4
├── v3.5/                 # Spark 3.5
└── v4.1/                 # Spark 4.1（当前为占位骨架，尚无源码）
```

顶层 `build.gradle` 通过 `sparkVersions` 系统属性决定编译哪些子版本：

```groovy
def sparkVersions = (System.getProperty("sparkVersions") != null
    ? System.getProperty("sparkVersions")
    : System.getProperty("defaultSparkVersions")).split(",")
if (sparkVersions.contains("3.5")) {
  apply from: file("$projectDir/v3.5/build.gradle")
}
```

### 2.2 单版本子模块组成（以 v3.5 为例）

每个 `vX.Y/` 目录下又分为三个 Gradle 子项目：

| 子项目 | 角色 | 产物 |
| --- | --- | --- |
| `spark/` | 主体 Java 代码（含少量 Scala），实现 Catalog/Source/Sink/Actions/Procedures | `iceberg-spark-3.5_<scalaVersion>` |
| `spark-extensions/` | Catalyst 扩展（Scala + ANTLR 语法），注入自定义解析器、分析规则、执行策略 | `iceberg-spark-extensions-3.5_<scalaVersion>` |
| `spark-runtime/` | 把 `iceberg-spark`、`iceberg-spark-extensions` 及其依赖 shade 成可直接 `--packages` 加载的 uber jar | `iceberg-spark-runtime-3.5_<scalaVersion>` |

### 2.3 为什么需要多版本

1. **Spark API 不兼容演进**：Spark 3.x 到 4.x 期间，DataSource V2、Catalyst 内部接口、Parser 注入点、`Predicate`/`V2Filter` 等多次破坏性变化，单一源码无法同时编译。例如 v3.2 仍依赖 `FileScanTaskSetManager`，而 v3.5 改用 `ScanTaskSetManager`；v3.5 新增了 `SparkV2Filters`、`SparkAggregates`、`SparkFunctionCatalog`、`SparkWriteRequirements`、`SparkWriteUtil` 等，对应 Spark 3.4/3.5 引入的 V2 过滤器和函数目录能力。
2. **Scala 版本耦合**：`spark-extensions` 由 Scala 编写并依赖 ANTLR，必须为每个 `sparkMajorVersion_scalaVersion` 组合单独构建。
3. **运行时隔离**：通过 `spark-runtime` 的 shade 机制，避免用户 classpath 中 Spark 自身依赖与 Iceberg 依赖冲突。
4. **统一抽象**：所有版本共用 `iceberg-api`、`iceberg-core`、`iceberg-data`、`iceberg-parquet`、`iceberg-orc`、`iceberg-arrow` 等核心模块，避免重复实现。
5. **`v4.1` 占位**：当前仅有空 `build/` 目录，为未来 Spark 4.1 适配预留位置。

## 4. 核心类与设计模式

### 4.1 Catalog 层：SparkCatalog 与 SparkSessionCatalog

- **`BaseCatalog`**：抽象基类，封装 `TableCatalog`/`SupportsNamespaces`/`FunctionCatalog` 的公共逻辑（如 identifier 解析、metadata 表路由、function catalog 委托）。通过正则模式 `at_timestamp_(\d+)`、`snapshot_id_(\d+)`、`branch_(.*)`、`tag_(.*)` 把"标识符后缀"转换为 time-travel/分支/标签语义。
- **`SparkCatalog`**：纯 Iceberg catalog 适配器。`buildIcebergCatalog` 委托 `CatalogUtil.buildIcebergCatalog` 构造 Hive/Hadoop/REST/Custom catalog；`loadTable(identifier, version|timestamp)` 实现 Spark 的 time-travel；`stageCreate/stageReplace/stageCreateOrReplace` 返回 `StagedSparkTable`（包装 `Transaction`），实现两阶段建表。
- **`SparkSessionCatalog<T extends TableCatalog & FunctionCatalog & SupportsNamespaces>`**：实现 `CatalogExtension`，作为「同名 catalog 中 Iceberg 与原生 session catalog 共存」的桥接器。当表能加载为 `SparkTable` 时走 Iceberg，否则委托给 `sessionCatalog`；可配置 `create-parquet-as-iceberg` 等参数把 `CREATE TABLE USING parquet` 自动转为 Iceberg 表。

**设计模式**：委托（Delegate）、适配器（Adapter）、工厂方法（`buildIcebergCatalog`/`buildSparkCatalog`）。

### 4.2 表与扫描：SparkTable 与 SparkScanBuilder

`SparkTable` 同时实现 `SupportsRead`/`SupportsWrite`/`SupportsDeleteV2`/`SupportsRowLevelOperations`/`SupportsMetadataColumns`，是 Spark 与 Iceberg 表对象的统一适配点：

```java
public class SparkTable implements Table,
    SupportsRead, SupportsWrite, SupportsDeleteV2,
    SupportsRowLevelOperations, SupportsMetadataColumns {
  // newScanBuilder: 根据 SCAN_TASK_SET_ID 走 SparkStagedScanBuilder，否则 SparkScanBuilder
  // newWriteBuilder: 普通 SparkWriteBuilder；若表为 PositionDeletesTable 走 SparkPositionDeletesRewriteBuilder
  // newRowLevelOperationBuilder: SparkRowLevelOperationBuilder (COPY-ON-WRITE / MERGE-ON-READ)
}
```

`SparkScanBuilder` 实现 `SupportsPushDownV2Filters`/`SupportsPushDownAggregates`/`SupportsPushDownRequiredColumns`/`SupportsReportStatistics`，把 Spark 谓词下推转 Iceberg `Expression`（`SparkV2Filters`/`SparkFilters`），并基于 `MetricsModes` 控制文件级统计裁剪。

`SparkScan` 体系采用 **模板方法 + 桥接**：`SparkScan` 抽象类持有 `Table`、`expectedSchema`、`filterExpressions`、`SparkReadConf`；具体子类 `SparkBatchQueryScan`、`SparkChangelogScan`、`SparkLocalScan` 决定如何枚举 `CombinedScanTask`/`FileScanTask`。

### 4.3 读取器族：BaseReader 继承体系

```
BaseReader<T, TaskT>             // 公共：Schema 修正、NameMapping、DeleteFilter、metadata 列填充
 ├── BaseBatchReader<ScanTask>   // 列式 / batch 输出
 │   └── BatchDataReader
 ├── BaseRowReader<ScanTask>      // 行式 InternalRow 输出
 │   ├── RowDataReader
 │   ├── ChangelogRowReader
 │   ├── EqualityDeleteRowReader
 │   └── PositionDeletesRowReader
```

`BaseReader` 把 `ContentFile`/`EncryptedInputFile` 解密、`NameMappingParser` 名字映射、`DeleteFilter`（position delete / equality delete 应用）、`MetadataColumns`（`spec_id`、`partition`、`file_path`、`row_position`、`_deleted`）等横切逻辑统一处理，子类只关注格式特定的列读取。

### 4.4 写入族：SparkWrite 与 SparkPositionDeltaWrite

`SparkWrite` 是抽象类，实现 `Write`/`RequiresDistributionAndOrdering`，定义多个内部类承载不同语义：

```
SparkWrite (abstract)
 ├── BatchAppend              // table.newAppend()
 ├── DynamicOverwrite          // table.newReplacePartitions()
 ├── OverwriteByFilter         // table.newOverwrite().overwriteByRowFilter(expr)
 ├── CopyOnWriteOperation      // 配合 SparkCopyOnWriteScan，COPY-ON-WRITE DELETE/UPDATE/MERGE
 ├── RewriteFiles              // 配合 FileRewriteCoordinator 替换指定文件组
 ├── StreamingAppend           // Structured Streaming append
 └── StreamingOverwrite        // Structured Streaming overwrite
```

`SparkPositionDeltaWrite` 实现 `DeltaWrite`，对应 MERGE-ON-READ 行级操作：通过 `PositionDeltaWriter` 同时输出数据文件与 position delete 文件，并基于 `IsolationLevel`（SERIALIZABLE/SNAPSHOT）做 `validateNoConflictingData`/`validateNoConflictingDeletes` 校验。

关键设计：

- **广播序列化表**：`SerializableTableWithSize.copyOf(table)` 把表元数据广播到 executor，避免每个 task 重新加载。
- **Writer 选择**：`useFanoutWriter` 由 `SparkWriteConf.useFanoutWriter(writeRequirements)` 决定，分布式模式强制时使用 `FanoutDataWriter`，否则用 `ClusteredDataWriter`/`RollingDataWriter` 按分区聚类。
- **WAP（Write-Audit-Publish）**：当 `wapEnabled && wapId != null` 时调用 `operation.stageOnly()`，把变更暂存到分支，不直接提交。
- **失败回滚**：`abort` 通过 `SparkCleanupUtil.deleteFiles` 删除 task 写出但未提交的数据文件；`CommitStateUnknownException` 时跳过清理以避免误删。

### 4.5 Actions 层

`SparkActions` 是 `ActionsProvider` 的 Spark 实现（**门面模式**），按工厂方法创建各类动作。继承体系：

```
BaseSparkAction (抽象：SparkSession、broadcast、JobGroup 管理、metadata 表读取)
 ├── BaseSnapshotUpdateSparkAction    // 提交快照类动作的公共逻辑
 │    ├── SnapshotTableSparkAction
 │    ├── MigrateTableSparkAction
 │    ├── RewriteDataFilesSparkAction
 │    ├── RewriteManifestsSparkAction
 │    └── RewritePositionDeleteFilesSparkAction
 ├── BaseTableCreationSparkAction
 │    ├── SnapshotTableSparkAction
 │    └── MigrateTableSparkAction
 ├── ExpireSnapshotsSparkAction
 ├── DeleteOrphanFilesSparkAction
 └── DeleteReachableFilesSparkAction
```

`RewriteDataFilesSparkAction` 支持 `BINPACK`/`SORT`/`ZORDER` 三种策略，对应 `SparkBinPackDataRewriter`/`SparkSortDataRewriter`/`SparkZOrderDataRewriter`/`SparkShufflingDataRewriter`，均实现 `FileRewriter`，通过 Spark Dataset 执行实际重写。

### 4.6 Procedures 层

`SparkProcedures` 用 `ImmutableMap<String, Supplier<ProcedureBuilder>>` 静态注册所有过程，过程名小写以匹配 Spark 大小写不敏感行为。`BaseProcedure` 提供 `modifyIcebergTable`/`withIcebergTable` 模板方法，封装"加载表 → 执行 → 刷新 Spark 缓存 → 关闭线程池"流程；按需创建 `ExecutorService`，结束后自动 `MoreExecutors.shutdownAndAwaitInvocation`。

### 4.7 Spark-Extensions：Catalyst 注入扩展

`IcebergSparkSessionExtensions` 通过 Spark 的 `inject*` 系列 hook 完成端到端注入：

```scala
extensions.injectParser { case (_, p) => new IcebergSparkSqlExtensionsParser(p) }
extensions.injectResolutionRule { spark => ResolveProcedures(spark) }
extensions.injectResolutionRule { _ => ProcedureArgumentCoercion }
extensions.injectOptimizerRule { _ => ReplaceStaticInvoke }
extensions.injectPlannerStrategy { spark => ExtendedDataSourceV2Strategy(spark) }
```

`IcebergSparkSqlExtensionsParser` 采用 **委托 + 前缀嗅探**：先对 SQL 文本做轻量关键字判断（`isIcebergCommand`），命中 Iceberg 语法（`call`、`alter table ... add/drop/replace partition field`、`write ordered by`、`set/drop identifier fields`、`create/replace/drop branch/tag`）才走自定义 ANTLR 解析；其余直接转发给 Spark 原生 `delegate`。ANTLR 解析采用 SLL 快速模式 → LL 精确模式两阶段回退策略，与 Spark 自身一致。`UnresolvedIcebergTable` 提取器通过 `EliminateSubqueryAliases` + `Spark3Util.catalogAndIdentifier` 在分析期判断 LogicalPlan 是否指向 Iceberg 表。

## 5. 关键流程

### 5.1 Spark 读取 Iceberg 表

1. Spark 通过 catalog name（如 `spark_catalog` 或 `iceberg_catalog`）找到 `SparkCatalog`/`SparkSessionCatalog`。
2. `SparkCatalog.loadTable(identifier)` 调用 `buildIcebergCatalog` 加载底层 `Catalog`，从 Iceberg catalog 获取 `Table`，包装为 `SparkTable`。若 identifier 含 `branch_xxx`/`tag_xxx`/`snapshot_id_xxx`/`at_timestamp_xxx` 后缀，则进一步设置 `branch` 或 `snapshotId`。
3. Spark 调 `SparkTable.newScanBuilder(options)`，得到 `SparkScanBuilder`（或 `SparkStagedScanBuilder`，当 `SCAN_TASK_SET_ID` 存在时用于 procedure 内部 staged scan）。
4. `SparkScanBuilder` 把 Spark `Predicate[]` 经 `SparkV2Filters`/`SparkFilters` 转 Iceberg `Expression`，应用 `Projections` 下推到分区；按 `SparkReadConf` 决定 `caseSensitive`、`splitSize`、`snapshotId`、`branch`、`as-of-timestamp`、`start-snapshot-id`/`end-snapshot-id` 等。
5. 构建底层 `BatchScan`/`IncrementalAppendScan`/`IncrementalChangelogScan`，调用 `planFiles()` 得到 `CloseableIterable<FileScanTask>`，按 `TableScanUtil.planTasks` 切分为 `CombinedScanTask`。
6. `SparkScan` 把 `CombinedScanTask` 转换为 `SparkInputPartition[]`（每个含一个 task group），返回 `Batch`/`Scan`。
7. Spark 启动 executor 执行 `PartitionReaderFactory.createReader()`，由 `SparkRowReaderFactory`/`SparkColumnarReaderFactory` 创建 `RowDataReader`/`BatchDataReader`，最终委托 `SparkParquetReaders`/`SparkOrcReader`/`SparkAvroReader` 读取实际文件。
8. `BaseReader` 在读取时应用 `DeleteFilter`、`NameMapping`、`MetadataColumns`，输出 `InternalRow`。

### 5.2 Spark 写入 Iceberg 表

1. `SparkTable.newWriteBuilder(LogicalWriteInfo)` 返回 `SparkWriteBuilder`，根据 `SparkWriteConf` 决定文件格式、目标大小、分布模式（`NONE`/`HASH`/`RANGE`）、是否 fanout writer、WAP 等。
2. `SparkWriteBuilder.build()` 根据操作类型返回 `SparkWrite` 实例：append、dynamic overwrite、overwrite by filter、copy-on-write、rewrite、streaming append/overwrite。`requiredDistribution()`/`requiredOrdering()`/`advisoryPartitionSizeInBytes()` 让 Spark 在执行前完成数据 shuffle。
3. Spark 调度 task 执行 `WriterFactory.createWriter()`，每个 task 持有广播的 `SerializableTableWithSize`，通过 `OutputFileFactory`/`FileWriterFactory` 创建 `RollingDataWriter`/`ClusteredDataWriter`/`FanoutDataWriter`，按 `PartitionKey` 写入数据文件。
4. task 完成后返回 `TaskCommit`（包含 `DataFile[]`）作为 `WriterCommitMessage`。
5. driver 端 `BatchWrite.commit(messages)` 收集所有 `DataFile`，构造 `AppendFiles`/`OverwriteFiles`/`ReplacePartitions`/`RowDelta`，调用 `commitOperation`：附加 `applicationId`、`extraSnapshotMetadata`、`CommitMetadata`、WAP staging、`toBranch`，最后 `operation.commit()`。
6. 若 commit 抛 `CommitStateUnknownException`，置 `cleanupOnAbort=false` 防止误删；其他异常 `abort()` 会通过 `SparkCleanupUtil` 删除 task 写出但未提交的文件。

### 5.3 行级操作（DELETE/UPDATE/MERGE）

1. Spark 调 `SparkTable.newRowLevelOperationBuilder(info)` → `SparkRowLevelOperationBuilder`。
2. 根据 `RowLevelOperationInfo.command`（DELETE/UPDATE/MERGE）和 `SparkWriteConf` 的 rewrite mode（`COPY_ON_WRITE`/`MERGE_ON_READ`）创建 `SparkCopyOnWriteOperation`（CoW）或 `SparkPositionDeltaWrite`（MoR）。
3. **COPY-ON-WRITE**：`SparkCopyOnWriteScan` 找出受影响文件 + 受影响行号，task 读出整行、应用变更，写出新数据文件，提交时通过 `OverwriteFiles` 替换受影响文件。
4. **MERGE-ON-READ**：`SparkPositionDeltaWrite` 用 `PositionDeltaWriter` 同时输出新数据文件和 position delete 文件，通过 `RowDelta` 提交；下游读取时由 `DeleteFilter` 应用 position delete。

### 5.4 Structured Streaming 读取

`SparkTable.newScanBuilder` 在 streaming 场景返回 `SparkMicroBatchStream`：

1. `latestOffset(startOffset)` 通过 `ContinuousEnumerationResult` 计算下一批 micro-batch，按 `splitSize`/`lookback`/`maxFilesPerMicroBatch` 切分。
2. `planInputPartitions(startOffset, endOffset)` 利用 `MicroBatches.microBatchesFor(...)` 把 snapshot 范围内的 `FileScanTask` 拆成 `MicroBatch`，再生成 `SparkInputPartition`。
3. 持久化 offset 到 checkpoint 目录，保证 exactly-once。

### 5.5 调用 CALL 存储过程

1. SQL `CALL catalog.ns.proc(args)` → `IcebergSparkSqlExtensionsParser.parsePlan` 走 ANTLR → 生成 `Call` LogicalPlan。
2. `ResolveProcedures` 通过 catalog 解析过程名并绑定 `BaseProcedure` 实例。
3. `ProcedureArgumentCoercion` 强转参数。
4. `ExtendedDataSourceV2Strategy` 把 `Call` 转为 `CallExec` 物理节点。
5. `CallExec.executeCollect` 调用 `Procedure.call()` 返回结果。

## 6. 与其他模块的关系

```
                    ┌──────────────────────────────────┐
                    │   iceberg-api / iceberg-core     │  ← 抽象层：Catalog/Table/Transaction/
                    │   iceberg-data / iceberg-common  │     Scan/AppendFiles/RowDelta/ActionsProvider
                    └──────────────┬───────────────────┘
                                   │ depends on
                                   ▼
┌────────────────┐    ┌──────────────────────────────────┐    ┌──────────────────────┐
│ spark-         │ ←─ │  spark/v3.5/spark                │ ─→ │ iceberg-parquet/orc/ │
│ extensions     │    │  (Catalog/Source/Sink/Actions/    │    │ avro/arrow           │
│ (Catalyst 注入) │    │   Procedures/Functions)           │    └──────────────────────┘
└────────────────┘    └──────────────┬───────────────────┘
                                   │ shaded by
                                   ▼
                          spark/v3.5/spark-runtime
                          (uber jar 给 --packages 使用)
```

- **向上**：通过 `spark-extensions` 的 `IcebergSparkSessionExtensions` 与 Spark Catalyst/Sql Parser 集成；通过 `SparkSessionExtensions` 配置 `spark.sql.extensions` 激活。
- **向下**：依赖 `iceberg-core` 的 `Catalog`/`Table`/`Transaction`/`TableScan`/`AppendFiles`/`RowDelta`/`ActionsProvider`，依赖 `iceberg-data` 的 `GenericRecord`、`DeleteFilter` 等，依赖 `iceberg-parquet`/`iceberg-orc`/`iceberg-avro`/`iceberg-arrow` 的格式读写器，依赖 `iceberg-bundled-guava`（shadow）、`iceberg-hive-metastore`（仅测试与 Hive catalog）。
- **横向**：与 `flink`/`mr`/`hive` 等其他引擎集成模块共享同一套核心 API；多版本子模块间共用核心抽象、仅 Spark 适配层不同。

## 7. 设计亮点与权衡

### 7.1 亮点

1. **委托 + 前缀嗅探解析器**：`IcebergSparkSqlExtensionsParser` 仅在 SQL 命中 Iceberg 关键字时才走 ANTLR，避免对普通 SQL 的性能与行为干扰；SLL/LL 两阶段解析与 Spark 原生解析器一致。
2. **统一 SparkSessionExtensions 入口**：单点 `IcebergSparkSessionExtensions` 注入 parser/analyzer/optimizer/planner 四阶段扩展，关闭扩展只需改一个配置项。
3. **`BaseCatalog` 模板抽取**：`metadata表路由`、`identifier 后缀解析`（time-travel/branch/tag）、`function catalog 委托`等通用逻辑集中在基类，`SparkCatalog` 与 `SparkSessionCatalog` 共享。
4. **`SparkSessionCatalog` 混合 catalog**：让 `spark_catalog`（HiveSessionCatalog）能同时支持 Iceberg 表和原生 Hive 表，平滑迁移；同时通过 `create-parquet-as-iceberg` 等参数实现"INSERT USING parquet → Iceberg"的隐式转换。
5. **`RequiresDistributionAndOrdering` 协议**：Spark 3.2+ 引入的写分布与排序协议，`SparkWrite`/`SparkPositionDeltaWrite` 通过 `SparkWriteRequirements` 把 Iceberg 表的 `write.distribution-mode`/`sort-order` 暴露给 Spark optimizer，让 Spark 自动完成 shuffle，无需在 Iceberg 内部实现 shuffle。
6. **WAP（Write-Audit-Publish）一等公民**：`stageOnly` + `wapId` 让数据先暂存到分支，审计通过后再 `cherrypick`，对生产 ETL 流程至关重要。
7. **`SerializableTableWithSize` 广播**：把表元数据序列化广播到 executor，避免每个 task 重复加载 metadata，减少 catalog 压力。
8. **Actions 的策略化重写器**：`RewriteDataFilesSparkAction` 通过 `FileRewriter` 接口抽象出 `BinPack`/`Sort`/`ZOrder`/`Shuffling` 多种策略，可插拔扩展。
9. **Procedures 模板方法**：`BaseProcedure.modifyIcebergTable` 统一处理"加载 → 执行 → 刷新 Spark 缓存 → 关闭线程池"，新过程只需实现 `call()`。
10. **多版本隔离**：通过 `spark-runtime` 的 shade 解决 Spark 自身依赖冲突，让用户可用 `--packages` 一行加载。

### 7.2 权衡

1. **代码重复 vs 兼容性**：每个 Spark 版本一份完整源码（而非条件分支）导致大量重复，但避免了 `if (sparkVersion >= 3.5)` 之类的运行时判断和编译期 API 漂移问题，是维护多 Spark 版本的常见取舍。
2. **依赖 Spark 内部 API**：`spark-extensions` 直接操作 `catalyst.plans.logical`、`catalyst.parser.extensions`、`execution.datasources.v2` 等 Spark 内部包，换取语法扩展能力，代价是每个 Spark 小版本可能需要适配。
3. **`spark-extensions` 与 `spark` 双 jar**：扩展 jar 必须先于主 jar 通过 `spark.sql.extensions` 激活，部署复杂度略增，但避免了主 jar 不需要扩展时被强加载。
4. **Spark vs Iceberg 元数据缓存**：Spark `CacheManager` 与 Iceberg `CachingCatalog` 双层缓存，需要在 procedures 中显式 `spark.sharedState.cacheManager.invalidateCachedTable` 防止读到旧数据，存在协调成本。
5. **`v4.1` 占位**：仅保留 build 骨架，反映 Spark 4.x 适配仍在进行，工程上先占位再补源码的策略。
6. **行级操作复杂度**：CoW 与 MoR 两条路径并存，`SparkPositionDeltaWrite` 与 `SparkCopyOnWriteOperation` 各有 isolation level 校验、`SparkCopyOnWriteScan`/`SparkPositionDeltaWrite` 的 split 规划逻辑，复杂度较高但提供灵活性。
