# iceberg-delta-lake 模块架构与设计思路

> 对应 Gradle 子模块 `:iceberg-delta-lake`，源码根目录 `delta-lake/`。
> 本文聚焦迁移逻辑，分析该模块如何将 Delta Lake 表转换为 Iceberg 表。

---

## 1. 模块定位

### 1.1 在 Iceberg 整体架构中的层次

`iceberg-delta-lake` 是 Iceberg 的**外部格式迁移支持模块**，位于 Iceberg 的 "Migration / Import" 工具层，与 `flink-migration` 等同级。它的核心职责是：把已有的 Delta Lake 表（基于 `_delta_log` 事务日志的湖仓格式）无损迁移为 Iceberg 表，使下游能继续基于 Iceberg 的快照、分区、Schema 演进能力进行读写。

在依赖层次上，它处于 Iceberg 模块图的上层，依赖关系自底向上大致为：

```
iceberg-bundled-guava (重打包 Guava)
        │
iceberg-api  ── iceberg-common ── iceberg-core ── iceberg-parquet
        │
iceberg-delta-lake   ← 本模块
        │
（可选）iceberg-spark-3.3 集成（仅 integration test 使用）
```

### 1.2 核心职责

| 职责 | 说明 |
| --- | --- |
| 读取 Delta Lake 元数据 | 通过 Delta Standalone API 读取 `DeltaLog`、`Snapshot`、`VersionLog`。 |
| Schema 转换 | 将 Delta 的 `StructType` 树转换为 Iceberg `Schema`，并分配字段 ID。 |
| 分区规格转换 | 把 Delta 的分区列列表映射为 Iceberg `PartitionSpec`（identity 分区）。 |
| 数据文件回放 | 按版本回放 `AddFile` / `RemoveFile` 动作为 Iceberg 的 `AppendFiles` / `DeleteFiles` / `OverwriteFiles`。 |
| 统计信息收集 | 从 Parquet 文件中提取 `Metrics`，写入 Iceberg manifest，保证查询优化可用。 |
| 溯源标记 | 为每个迁移的 Delta 版本打 tag，建立 Iceberg 快照与 Delta 版本/时间戳的映射。 |

### 1.3 边界与非目标

- **只迁移 Parquet 数据文件**：通过路径后缀 `.parquet` 判断文件格式，其它格式直接抛 `ValidationException`。
- **不做在线双写或 CDC 同步**：本模块是"一次性快照迁移"工具，迁移完成后 Delta 表与 Iceberg 表解耦。
- **不在迁移过程中改写数据文件**：原 Delta 的 Parquet 文件被直接登记为 Iceberg 数据文件（路径复用），不进行 ETL。
- **仅 Spark 集成测试**：`src/integration/java` 仅在 Spark 3.3 可用时构建，主源码不绑定具体引擎。

## 3. 核心类与设计模式

### 3.1 类关系图

```

            │   extends Action<SnapshotDeltaLakeTable, Result>    │
```

### 3.2 设计模式一览

#### 模式 1：Service Provider Interface (SPI) + 默认实现单例

`DeltaLakeToIcebergMigrationActionsProvider` 是迁移能力的对外契约。它通过 `defaultActions()` 返回嵌套类 `DefaultDeltaLakeToIcebergMigrationActions` 的私有静态单例：

- **解耦创建与使用**：Spark/Flink 等引擎依赖此接口而非具体实现，可在生产环境替换为自定义实现。
- **单例 + 私有构造**：避免重复实例化，同时禁止外部直接 new。
- **接口默认方法**：`snapshotDeltaLakeTable(...)` 在接口上以 default 方法提供"new BaseSnapshotDeltaLakeTableAction"，引擎如不替换就直接用默认实现。

#### 模式 2：Builder / 链式配置 + Action 框架

`SnapshotDeltaLakeTable` 继承自 Iceberg 通用 `Action<Self, Result>` 接口，所有配置方法返回 `this`，链式编排：

```java
provider.snapshotDeltaLakeTable(deltaLoc)
    .as(identifier)
    .icebergCatalog(catalog)
    .deltaLakeConfiguration(conf)
    .tableLocation(loc)
    .tableProperty(k, v)
    .execute();
```

- **契约/实现分离**：接口定义行为契约，`BaseSnapshotDeltaLakeTableAction` 是包级可见的实现类（`class`，非 `public`），只能通过 SPI 创建。
- **Immutables 生成 Result**：`@Value.Immutable` 注解让注解处理器生成 `ImmutableSnapshotDeltaLakeTable.Result`，保证结果对象不可变且线程安全。

#### 模式 3：Visitor（访问者）

`DeltaLakeDataTypeVisitor<T>` 是经典访问者模式：

- **为何用 Visitor**：Delta Lake 的 `DataType` 类层级来自第三方依赖 `io.delta.standalone.types`，无法在其内部加方法。访问者模式把"对类型结构的遍历"与"对每个节点的处理"分离，外部即可扩展行为而无需修改既有类层级。
- **泛型返回值 `T`**：同一个遍历骨架既可用于"转换为 Iceberg 类型"（`DeltaLakeTypeToType` 返回 `org.apache.iceberg.types.Type`），也可在未来用于其他用途（如校验、收集信息）。
- **递归自驱动**：`visit(DataType, visitor)` 是静态入口，内部递归调用自身；子类只需实现叶子回调。

#### 模式 4：Template Method（模板方法）

`DeltaLakeDataTypeVisitor.visit(...)` 提供了遍历骨架（先递归子节点，再回调本节点），子类只需实现 `struct/field/array/map/atomic` 五个回调，无需关心遍历顺序。

#### 模式 5：单事务编排（Transaction Script）

`BaseSnapshotDeltaLakeTableAction.execute()` 用一个 Iceberg `Transaction` 把所有变更原子化提交：

- 创建表事务（`newCreateTableTransaction`）
- 写入 NameMapping 属性
- 提交初始快照
- 逐版本回放变更
- 最终 `commitTransaction()` 一次性提交

要么全部生效，要么表不存在，保证迁移的原子性。

## 4. 关键流程

### 4.1 端到端迁移流程

```
用户调用 execute()
        │
        ▼
[1] 参数校验：icebergCatalog/identifier/deltaLog 非空、Delta 表存在
        │
        ▼
[2] deltaLog.update() 获取最新 Snapshot
        │
        ▼
[3] Schema 转换：convertDeltaLakeSchema()
    └─ DeltaLakeDataTypeVisitor.visit(deltaSchema, new DeltaLakeTypeToType(deltaSchema))
        │
        ▼
[4] 分区规格转换：getPartitionSpecFromDeltaSnapshot()
    └─ 遍历 partitionColumns，对每个列 builder.identity(name)
        │
        ▼
[5] 在 Iceberg Catalog 创建建表事务 newCreateTableTransaction(...)
        │
        ▼
[6] 写入 DEFAULT_NAME_MAPPING 属性
    └─ NameMappingParser.toJson(MappingUtil.create(schema))
        │
        ▼
[7] 提交初始可构造快照 commitInitialDeltaSnapshotToIcebergTransaction()
    └─ 从 deltaStartVersion 起逐版本尝试，遇不可构造则 version++ 重试
    └─ 成功 → AppendFiles + tagCurrentSnapshot
        │
        ▼
[8] 逐版本回放 deltaLog.getChanges(startVersion+1, false)
    └─ 每条 VersionLog：
        ├─ 过滤 AddFile/RemoveFile
        ├─ buildDataFileFromAction() 转 Iceberg DataFile
        ├─ 选择操作类型：
        │   • 既有 Add 又有 Remove → OverwriteFiles
        │   • 仅 Add              → AppendFiles
        │   • 仅 Remove           → DeleteFiles
        │   • 都没有              → 空追加（只为打 tag）
        └─ tagCurrentSnapshot()
        │
        ▼
[9] icebergTransaction.commitTransaction()  ← 原子提交
        │
        ▼
[10] 返回 Result { snapshotDataFilesCount }
```

### 4.2 Schema 转换与字段 ID 分配策略

`DeltaLakeTypeToType` 在 `struct()` 中对字段 ID 采取**双策略**：

- **根 Struct**：字段 ID = 序号 `i`（`isRoot` 通过**引用相等** `root == struct` 判断）。这与 Iceberg 默认行为一致，便于与已有表 schema 对齐。
- **嵌套类型**（List/Map 元素、Map 的 key/value、嵌套 Struct 字段）：通过 `getNextId()` 自增分配，初值从 `root.getFields().length` 开始，避免与根字段 ID 冲突。

字段 ID 是 Iceberg schema 演进和字段追踪的基础（按 ID 而非名字定位列），所以分配必须全局唯一且稳定。

类型映射要点：

| Delta Lake 类型 | Iceberg 类型 | 备注 |
| --- | --- | --- |
| BooleanType | BooleanType | |
| ByteType / ShortType / IntegerType | IntegerType | 三者统一为 Integer |
| LongType | LongType | |
| FloatType / DoubleType | FloatType / DoubleType | |
| StringType | StringType | |
| DateType | DateType | |
| TimestampType | TimestampType.withZone() | **统一带时区** |
| DecimalType | DecimalType(precision, scale) | 保留精度 |
| BinaryType | BinaryType | |
| StructType | Types.StructType | 递归 |
| ArrayType | Types.ListType | 按 containsNull 决定 optional/required |
| MapType | Types.MapType | key 始终 required，value 按 valueContainsNull |
| 其它 | 抛 ValidationException | 不支持 |

### 4.3 初始快照的容错回退

Delta Lake 的早期版本可能因 VACUUM 清理或 checkpoint 截断而**不可构造**（数据文件已被物理删除）。`commitInitialDeltaSnapshotToIcebergTransaction` 的策略：

```
从 deltaStartVersion 到 latestVersion 逐版本尝试：
    try:
        取该版本全部 AddFile
        转为 Iceberg DataFile
        AppendFiles.commit()
        tagCurrentSnapshot()
        return 该版本号
    catch NotFoundException | IllegalArgumentException | DeltaStandaloneException:
        version++ 继续
若全部失败 → 抛 ValidationException("contains no constructable snapshot")
```

这是一种"从最早可构造快照起步"的策略，最大限度保留历史。

### 4.4 版本日志回放的四分支决策

每条 `VersionLog` 包含一组 `Action`，过滤后只保留 `AddFile` / `RemoveFile`：

| filesToAdd | filesToRemove | 选择的 Iceberg 操作 | 场景 |
| --- | --- | --- | --- |
| >0 | >0 | `OverwriteFiles` | DELETE/UPDATE（删旧文件 + 加新文件） |
| >0 | =0 | `AppendFiles` | INSERT |
| =0 | >0 | `DeleteFiles` | 整文件删除 |
| =0 | =0 | `AppendFiles`（空追加） | 仅元数据变更，但仍需打 tag 留痕 |

### 4.5 DataFile 构建流程

`buildDataFileFromAction(action, table)` 是迁移的核心适配点：

1. 按 Action 类型（AddFile/RemoveFile）提取 `path`、`size`、`partitionValues`。
2. `getFullFilePath()` 处理相对路径（拼接 Delta 表根路径）和 URL 解码。
3. 校验 `partitionValues` 非 null（非分区表也要求空 Map 而非 null）。
4. `determineFileFormatFromPath()` 按后缀判断格式，**目前仅支持 `.parquet`**。
5. 通过 `deltaLakeFileIO.newInputFile(fullFilePath)` 打开文件，校验存在；若 Action 未带 size 则从文件系统读 `getLength()`。
6. 基于 `MetricsConfig` 和 `NameMapping` 调 `ParquetUtil.fileMetrics()` 提取列级统计。
7. 按分区字段名拼接分区路径字符串（`field1=val1/field2=val2`），用 `DataFiles.builder(spec)` 构建。

### 4.6 溯源 Tag 机制

`tagCurrentSnapshot(deltaVersion, transaction)` 为每个 Iceberg 快照打两个标签：

- `delta-version-<版本号>`：始终打。
- `delta-ts-<时间戳>`：若该 Delta 版本有提交时间戳则打。

这样迁移后的 Iceberg 表可通过 tag 反查原始 Delta 版本与时间，便于审计与对账。

## 5. 与其他模块的关系

### 5.1 依赖图

```
iceberg-delta-lake
├── iceberg-bundled-guava (shadow configuration)   ← 重打包 Guava
├── iceberg-api                                     ← Catalog/Schema/TableIdentifier/Action
├── iceberg-common                                  ← 通用工具
├── iceberg-core                                    ← Transaction/AppendFiles/...
├── iceberg-parquet                                 ← ParquetUtil 提取 Metrics
├── jackson-bom / jackson-databind                  ← JSON 处理
├── immutables (annotationProcessor + compileOnly)  ← 生成 Immutable Result
├── io.delta:delta-standalone_<scala> (compileOnly) ← Delta Standalone API
└── hadoop2-common (compileOnly)                    ← Hadoop Configuration
```

注意几个关键点：

- `iceberg-bundled-guava` 以 `configuration: 'shadow'` 方式依赖，引用的是**重打包后的 Guava**（包名 `org.apache.iceberg.relocated.com.google.common.*`），避免与用户 classpath 上的 Guava 版本冲突。模块内所有 Guava 引用都走 relocated 包名。
- `delta-standalone` 与 `hadoop2-common` 是 `compileOnly`，运行时由调用方（如 Spark 集成）提供，避免把 Delta/Hadoop 强行打入产物。
- `iceberg-parquet` 用于读取数据文件统计指标。

### 5.2 被谁使用

- **集成测试**：`src/integration/java/.../DeltaLakeToIcebergMigrationSparkIntegration.java` 提供 Spark 调用示例，被 `TestSnapshotDeltaLakeTable` 端到端测试使用。
- **下游引擎**：理论上任何能拿到 `SparkSession` / `Catalog` / `Configuration` 的引擎都可调用 `DeltaLakeToIcebergMigrationActionsProvider.defaultActions().snapshotDeltaLakeTable(...)` 发起迁移。

### 5.3 上游依赖（外部）

- **Delta Standalone API**（`io.delta.standalone.*`）：提供 `DeltaLog`、`Snapshot`、`VersionLog`、`AddFile`、`RemoveFile`、`DataType` 等。这是迁移的"源端契约"。
- **Hadoop Configuration**：用于初始化 `DeltaLog` 和 `HadoopFileIO`。

## 6. 设计亮点与权衡

### 6.1 设计亮点

1. **契约/实现分离 + SPI**：动作接口对外暴露，实现包级可见，引擎可替换；通过单例默认实现降低常见场景的使用成本。
2. **Visitor 模式解耦类型转换**：Delta 类型层级不可改，Visitor 让转换逻辑可扩展、可复用；泛型返回值让骨架未来可服务于其他用途。
3. **字段 ID 双策略分配**：根字段用序号（与 Iceberg 默认对齐），嵌套字段自增（全局唯一），兼顾兼容性与正确性。
4. **单事务原子提交**：所有变更在一个 `Transaction` 内，要么表完整创建，要么不存在，避免半成品状态。
5. **增量回放还原历史**：先提交初始可构造快照，再逐版本回放，把 Delta 的版本演变精确还原为 Iceberg 快照序列，迁移后表可查任意历史时刻。
6. **容错跳过不可构造快照**：自动从下一版本重试，最大化保留历史，对 VACUUM 后的表也能迁移。
7. **NameMapping 解决字段 ID 对齐**：迁移时写入 `DEFAULT_NAME_MAPPING`，让 Iceberg 能按字段名匹配读取旧 Parquet 文件的列统计（旧文件没有 Iceberg 字段 ID 元数据）。
8. **Tag 溯源**：每个快照打 `delta-version-*` / `delta-ts-*` 标签，迁移后可审计、可对账。
9. **数据文件零拷贝**：原 Parquet 文件路径直接登记为 Iceberg 数据文件，不做 ETL，迁移速度快、不占用额外存储。

### 6.2 权衡与局限

1. **只支持 Parquet**：`determineFileFormatFromPath` 仅认 `.parquet`，Delta 表若用 ORC/Avro 等格式则无法迁移。
2. **依赖 Delta Standalone API**：只能迁移 Delta Standalone 支持的版本范围，新版 Delta 特性（如 CDF、Deletion Vectors）可能不在覆盖范围内。
3. **集成测试绑定 Spark 3.3**：`src/integration/java` 仅在 `sparkVersions.contains("3.3")` 时构建，新版 Spark 需要自行适配。
4. **`deltaLakeConfiguration` 必须显式调用**：动作不会自动推断 Hadoop 配置，调用方必须显式传入，否则 `execute()` 校验失败。
5. **`getChanges(startVersion+1, false)`**：第二个参数 `false` 表示遇到数据丢失不抛异常，会静默跳过——这提升了容错性，但也可能在迁移中"丢版本"而不报错，需要调用方关注日志。
6. **`TimestampType` 统一带时区**：Delta 的 `TimestampType` 一律映射为 `Types.TimestampType.withZone()`，对带时区语义是合理的，但对原始"不带时区"的 TimestampNTZ 场景可能产生语义偏差（Delta Standalone 老版本未区分 NTZ）。
7. **`additionalPropertiesBuilder` 是字段级可变状态**：多次调用 `tableProperty`/`tableProperties` 会累积；同一 key 后写覆盖先写。这是 Builder 的常见做法，但意味着动作实例不可重入、不可并发执行。
8. **`@SuppressWarnings("ReferenceEquality")`**：根 Struct 判断用引用相等而非值相等，依赖"传入的根 Struct 就是构造时保存的同一引用"。这是刻意设计（性能 + 简单），但要求调用方不重建 Struct 实例。

### 6.3 扩展点

- **替换实现**：实现 `DeltaLakeToIcebergMigrationActionsProvider` 接口，返回自定义的 `SnapshotDeltaLakeTable` 即可替换默认迁移逻辑（如增加文件格式支持、改变 tag 命名、写入额外属性等）。
- **扩展类型访问者**：继承 `DeltaLakeDataTypeVisitor<T>` 实现新的访问者，可对 Delta schema 做校验、统计或其他转换，复用同一套遍历骨架。
