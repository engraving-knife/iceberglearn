# iceberg-bundled-guava 模块架构与设计思路

> 对应 Gradle 子模块 `:iceberg-bundled-guava`，源码根目录 `bundled-guava/`。
> 本文聚焦 Guava 重打包（shade + relocate）机制。

---

## 1. 模块定位

### 1.1 在 Iceberg 整体架构中的层次

`iceberg-bundled-guava` 是 Iceberg **最底层的基础设施模块**，位于依赖图的根部。它本身不包含任何业务逻辑，唯一的源码类 `GuavaClasses` 只是一个"声明清单"，真正的工作由 Gradle Shadow 插件在构建期完成。

依赖层次示意：

```
                 ┌─────────────────────────────┐
                 │  iceberg-bundled-guava      │  ← 本模块（重打包后的 Guava）
                 │  产物：shadow configuration │
                 └──────────────┬──────────────┘
                                │ 被所有上层模块以
                                │ configuration: 'shadow' 依赖
            ┌───────────────────┼───────────────────┐
            ▼                   ▼                   ▼
      iceberg-api         iceberg-common       iceberg-core
            │                   │                   │
            └─────────… 所有引擎集成模块（spark/flink/hive/…）…─┘
                  统一以 org.apache.iceberg.relocated.com.google.common.*
                  引用 Guava 工具类
```

### 1.2 核心职责

| 职责 | 说明 |
| --- | --- |
| 重打包 Guava | 把上游 `com.google.guava:guava` 的字节码打入本模块产物 jar。 |
| 重命名包（relocate） | 把 `com.google.common.*` 改写为 `org.apache.iceberg.relocated.com.google.common.*`，并对所有引用同步改写。 |
| 裁剪（minimize） | 只保留实际被引用的类，减小产物体积。 |
| 提供白名单 | 通过 `GuavaClasses` 静态块强制保留 Iceberg 实际需要的 Guava 类，避免被 minimize 误删。 |
| 暴露 shadow configuration | 让其他模块以 `project(path: ':iceberg-bundled-guava', configuration: 'shadow')` 方式依赖，获得重打包后的 Guava。 |

### 1.3 为什么需要这个模块

Iceberg 在内部大量使用 Guava（`Preconditions`、`ImmutableMap`、`Lists`、`Joiner`、`Hashing` 等）。但 Guava 是 Java 生态中最常见的"依赖冲突源"——Spark、Hive、Hadoop、Flink 各自绑定不同版本，且 Guava 在大版本间有破坏性变更（如 `Stopwatch.createStarted` 在 16+ 才有）。

如果 Iceberg 直接 `implementation 'com.google.guava:guava'`，就会和宿主引擎的 Guava 在同一 classpath 上打架，导致运行时 `NoSuchMethodError` / `ClassNotFoundException`。

**解决方案**：把 Guava 重打包到 Iceberg 私有命名空间 `org.apache.iceberg.relocated.com.google.common.*`，与外界隔离。这样：

- Iceberg 内部总能用到自己想要的 Guava 版本。
- 不会泄漏给宿主，也不会被宿主的不同版本污染。
- 宿主可以继续用它自己的 Guava，互不干扰。

这是 Apache 生态（Avro、Parquet、HBase 等）常见的"shaded dependency"实践。

## 2. 包结构概览

模块源码极简，只有一个类：

```
bundled-guava/
├── LICENSE                                  # Guava 的 Apache 2.0 许可证
├── NOTICE                                   # 法律声明
├── src/
│   └── main/java/org/apache/iceberg/
│       └── GuavaClasses.java               # 唯一源码：Guava 类白名单
└── build.gradle                            # 构建配置（在仓库根 build.gradle 中，约第 245 行）
```

构建产物（`build/libs/`）：

- `iceberg-bundled-guava-<version>.jar`：**shadow jar**（重打包后的 Guava，是真正被使用的产物）。
- `iceberg-bundled-guava-<version>-empty.jar`：本模块自身源码编译出的"空壳" jar（仅含 `GuavaClasses.class`），通过 `archiveClassifier.set('empty')` 标记，正常不会被依赖。
- `-sources.jar` / `-javadoc.jar` / `-tests.jar`：辅助产物。

shadow jar 内部结构（实测）：

```
iceberg-bundled-guava-1.5.0-SNAPSHOT.jar
├── META-INF/
│   ├── MANIFEST.MF
│   ├── LICENSE                              # 打入的许可证
│   ├── proguard/                            # Guava 自带的 proguard 配置
│   └── maven/com.google.guava/guava/...     # Guava 原 pom
├── org/apache/iceberg/
│   ├── GuavaClasses.class                   # 白名单类
│   └── relocated/com/google/common/
│       ├── base/                            # Preconditions, Joiner, ...
│       ├── collect/                         # ImmutableMap, Lists, ...
│       ├── hash/                            # Hashing, Hasher, ...
│       ├── io/                              # Files, Resources, ...
│       ├── primitives/                      # Bytes, ...
│       ├── util/concurrent/                 # MoreExecutors, ThreadFactoryBuilder, ...
│       └── ...（共约 1143 个 .class，覆盖 Guava 主要包）
```

## 3. 核心类与设计模式

### 3.1 唯一类：`GuavaClasses`

`src/main/java/org/apache/iceberg/GuavaClasses.java` 是模块唯一源码。它的设计非常巧妙：

```java
public class GuavaClasses {
  static {
    VisibleForTesting.class.getName();
    Joiner.class.getName();
    MoreObjects.class.getName();
    Objects.class.getName();
    Preconditions.class.getName();
    Splitter.class.getName();
    Throwables.class.getName();
    BiMap.class.getName();
    FluentIterable.class.getName();
    ImmutableBiMap.class.getName();
    ImmutableList.class.getName();
    ImmutableMap.class.getName();
    ImmutableSet.class.getName();
    Iterables.class.getName();
    Iterators.class.getName();
    ListMultimap.class.getName();
    Lists.class.getName();
    MapMaker.class.getName();
    Maps.class.getName();
    Multimap.class.getName();
    Multimaps.class.getName();
    Ordering.class.getName();
    Sets.class.getName();
    Streams.class.getName();
    Hasher.class.getName();
    HashFunction.class.getName();
    Hashing.class.getName();
    Files.class.getName();
    Bytes.class.getName();
    Resources.class.getName();
    MoreExecutors.class.getName();
    ThreadFactoryBuilder.class.getName();
    Iterables.class.getName();
    CountingOutputStream.class.getName();
    Suppliers.class.getName();
    Stopwatch.class.getName();
  }
}
```

#### 设计要点

1. **声明即保留**：Shadow 插件的 `minimize()` 会做依赖图分析，只保留"被字节码实际引用"的类。本类通过静态初始化块调用 `X.class.getName()`，在不真正调用业务方法的前提下让这些 Guava 类进入依赖图，从而被打入最终 jar。`@SuppressWarnings("ReturnValueIgnored")` 标注表明返回值被故意忽略——目的就是触发类加载，不是用返回值。

2. **集中可维护**：所有需要保留的 Guava 类集中于这一处清单，方便增删与审查。新增使用某个 Guava 类时需要同步增补此清单，否则 minimize 可能把它裁掉。

3. **不调用业务逻辑**：只用 `Class.getName()` 触发类加载，不调用任何 Guava 方法，避免引入不必要的运行期副作用（如初始化开销、副作用静态块）。

4. **来源借鉴**：类注释明确说明设计启发自 Apache Avro 项目的同名 `GuavaClasses`（`https://github.com/apache/avro/blob/release-1.8.2/lang/java/guava/...`），是 Apache 生态成熟的实践。

### 3.2 构建配置：Shadow 插件

构建逻辑在仓库根 `build.gradle` 第 245 行起的 `project(':iceberg-bundled-guava')` 块：

```groovy
project(':iceberg-bundled-guava') {
  apply plugin: 'com.github.johnrengelman.shadow'

  tasks.jar.dependsOn tasks.shadowJar

  dependencies {
    compileOnly(libs.guava.guava) {                // ← Guava 仅编译期依赖
      exclude group: 'com.google.code.findbugs'
      exclude group: 'com.google.errorprone'
      exclude group: 'com.google.j2objc'
    }
  }

  shadowJar {
    archiveClassifier.set(null)                     // shadow jar 不带 classifier，作为默认产物
    configurations = [project.configurations.compileClasspath]
    zip64 true                                      // 因类多需 zip64

    from(projectDir) { include 'LICENSE'; include 'NOTICE' }   // 打入法律文件

    dependencies {
      exclude(dependency('org.slf4j:slf4j-api'))    // 不带入 slf4j
      exclude(dependency('org.checkerframework:checker-qual'))
    }

    relocate 'com.google.common',
             'org.apache.iceberg.relocated.com.google.common'   // ← 关键：包重命名

    minimize()                                      // 裁剪未引用类
  }

  jar {
    archiveClassifier.set('empty')                  // 普通 jar 标记为 empty，避免被误用
  }
}
```

#### 关键配置项解读

| 配置 | 作用 | 设计意图 |
| --- | --- | --- |
| `apply plugin: 'com.github.johnrengelman.shadow'` | 引入 Shadow 插件 | 提供 `shadowJar` 任务，支持 relocate/minimize/合并 jar |
| `compileOnly(libs.guava.guava)` | Guava 仅编译期 | 不让 Guava 作为运行时传递依赖泄漏给下游；运行时用 shadow jar 提供 |
| `exclude group: 'com.google.code.findbugs'` 等 | 排除 Guava 的传递依赖 | findbugs 可能 LGPL，errorprone/j2objc 不必要，避免许可与体积问题 |
| `archiveClassifier.set(null)` | shadow jar 作为默认产物 | 让 `configuration: 'shadow'` 解析到无 classifier 的 jar |
| `zip64 true` | 启用 ZIP64 | Guava 类太多，普通 zip 偏移超 32 位会失败 |
| `from(projectDir) { include 'LICENSE'; 'NOTICE' }` | 打入法律文件 | 重分发时满足 Apache 2.0 许可证要求 |
| `exclude(dependency('org.slf4j:slf4j-api'))` | 排除 slf4j | 避免把日志框架打入，由宿主提供 |
| `exclude(dependency('org.checkerframework:checker-qual'))` | 排除 checker-qual | Guava 用它做空值注解，运行时不必要 |
| `relocate 'com.google.common', 'org.apache.iceberg.relocated.com.google.common'` | **核心：包重命名** | 把所有 `com.google.common.*` 字节码改写到 Iceberg 私有命名空间，同时改写所有引用 |
| `minimize()` | 裁剪未引用类 | 减小产物体积，只保留 `GuavaClasses`（及它引用的）Guava 类 |
| `jar { archiveClassifier.set('empty') }` | 普通 jar 标 empty | 防止下游误依赖到只含 `GuavaClasses` 的空壳 jar |

### 3.3 设计模式

#### 模式 1：Shaded Dependency（依赖隔离）

这是本模块的核心模式：把第三方依赖重打包到私有命名空间，与外界隔离。好处：

- **版本独立性**：Iceberg 用自己测试过的 Guava 版本，不受宿主影响。
- **无泄漏**：重打包后的 Guava 不会出现在宿主的 classpath 上，不会污染宿主。
- **二进制兼容性可控**：升级 Guava 时只需重新打包本模块并验证。

#### 模式 2：Manifest / White-list（白名单保留）

`GuavaClasses` 起到"白名单"作用：在 minimize 阶段强制保留指定 Guava 类。这是因为：

- Shadow 的 minimize 基于字节码引用分析，但有些引用是反射/动态的，分析不到。
- 把"需要保留哪些 Guava 类"集中声明，便于审查与维护，避免散落到各业务类。
- 新增使用某个 Guava 类时，必须同步增补此清单——这是一条隐式约定。

#### 模式 3：Configuration 分离（shadow configuration）

本模块对外暴露 `shadow` configuration，其他模块以：

```groovy
implementation project(path: ':iceberg-bundled-guava', configuration: 'shadow')
```

方式依赖。这样：

- 下游拿到的是 shadow jar（重打包后的 Guava），不是空壳 jar。
- 依赖关系语义清晰：明确表示"我要的是 shaded 产物"。
- 全仓库统一用法，所有上层模块（api/core/spark/flink/hive/...）都这样依赖，保证一致性。

## 4. 关键流程

### 4.1 构建期流程（shadow jar 如何生成）

```
gradle :iceberg-bundled-guava:build
        │
        ▼
[1] compileJava
    └─ 编译 GuavaClasses.java（compileOnly 依赖 guava，不传递）
        │
        ▼
[2] jar（普通 jar）
    └─ 仅含 GuavaClasses.class，archiveClassifier = 'empty'
        │
        ▼
[3] shadowJar（核心任务，jar 依赖它）
    ├─ 输入：project.configurations.compileClasspath（含 guava 及其排除后的传递依赖）
    ├─ 步骤 a：合并 guava 的所有 .class
    ├─ 步骤 b：relocate com.google.common → org.apache.iceberg.relocated.com.google.common
    │         （改写 .class 文件内的包名 + 所有引用）
    ├─ 步骤 c：exclude slf4j-api、checker-qual
    ├─ 步骤 d：from(projectDir) 打入 LICENSE / NOTICE
    ├─ 步骤 e：minimize() 依赖图分析，保留被引用的类
    │         └─ GuavaClasses 的静态块引用了一批 Guava 类 → 这些类被保留
    └─ 输出：iceberg-bundled-guava-<version>.jar（无 classifier）
        │
        ▼
[4] 上游模块 resolution
    └─ implementation project(path: ':iceberg-bundled-guava', configuration: 'shadow')
       → 解析到步骤 3 的 shadow jar
```

### 4.2 运行期流程（上层如何使用）

上层模块源码中所有 Guava 引用都走 relocated 包名：

```java
// 例：iceberg-api 的 FileFormat.java
import org.apache.iceberg.relocated.com.google.common.base.Preconditions;

// 例：iceberg-delta-lake 的 BaseSnapshotDeltaLakeTableAction.java
import org.apache.iceberg.relocated.com.google.common.base.Preconditions;
import org.apache.iceberg.relocated.com.google.common.collect.ImmutableMap;
import org.apache.iceberg.relocated.com.google.common.collect.ImmutableSet;
import org.apache.iceberg.relocated.com.google.common.collect.Lists;
```

运行时类加载：

```
JVM 加载 org.apache.iceberg.relocated.com.google.common.base.Preconditions
  → 在 classpath 上找 org/apache/iceberg/relocated/com/google/common/base/Preconditions.class
  → 命中 iceberg-bundled-guava-<version>.jar 内的对应条目
  → 加载成功，与宿主的 com.google.common.base.Preconditions 完全隔离
```

### 4.3 升级 Guava 的流程

1. 修改版本目录（`libs.versions.toml` 或等价配置）中 `guava` 的版本。
2. 重新构建 `:iceberg-bundled-guava`，确认 shadow jar 生成成功。
3. 若新增使用了 `GuavaClasses` 清单外的 Guava 类，需同步增补清单。
4. 跑全仓库测试，验证 relocate 后的类与上游兼容。

## 5. 与其他模块的关系

### 5.1 被谁依赖

几乎所有 Iceberg 模块都依赖本模块（在 `build.gradle` 中以 `configuration: 'shadow'` 方式）。统计仓库根 `build.gradle` 中出现 `iceberg-bundled-guava` 的次数超过 15 处，覆盖：

- `iceberg-api`、`iceberg-common`、`iceberg-core`
- `iceberg-parquet`、`iceberg-orc`、`iceberg-arrow`
- `iceberg-hive-metastore`、`iceberg-hive3`、`iceberg-hive-runtime`
- `iceberg-spark-*`（各 Spark 版本）
- `iceberg-flink-*`、`iceberg-flink-runtime`
- `iceberg-aws`、`iceberg-gcp`、`iceberg-azure`
- `iceberg-delta-lake`、`iceberg-bom` 等

### 5.2 全局排除原始 Guava

仓库根 `build.gradle` 有一段全局配置：

```groovy
if (project.name != 'iceberg-bundled-guava') {
  exclude group: 'com.google.guava', module: 'guava'
}
```

含义：除本模块外，所有模块都**禁止**直接依赖原始 `com.google.guava:guava`。这从构建层面强制所有 Guava 使用都走 relocated 路径，杜绝误用。

### 5.3 上游依赖

- **`com.google.guava:guava`**（compileOnly）：被打包的源头。
- 排除的传递依赖：`com.google.code.findbugs`、`com.google.errorprone`、`com.google.j2objc`、`org.slf4j:slf4j-api`、`org.checkerframework:checker-qual`。

### 5.4 对外暴露

- **`shadow` configuration**：供其他模块依赖，解析到 shadow jar。
- **relocated 包名**：`org.apache.iceberg.relocated.com.google.common.*`，这是全仓库统一引用 Guava 的命名空间。

## 6. 设计亮点与权衡

### 6.1 设计亮点

1. **彻底解决 Guava 依赖冲突**：通过 relocate 到私有命名空间，Iceberg 内部 Guava 与宿主 Guava 物理隔离，杜绝 `NoSuchMethodError` 类问题。这是 Iceberg 能在 Spark/Hive/Flink 等复杂 classpath 环境稳定运行的关键基础设施之一。

2. **构建期 vs 运行期分离**：
   - 构建期：Shadow 插件做字节码改写、合并、裁剪。
   - 运行期：零额外开销，就是普通 jar 加载。
   不引入运行期代理、类加载器魔术，行为可预测。

3. **白名单集中管理**：`GuavaClasses` 把"需要保留哪些 Guava 类"集中到一处，可审查、可维护。比让 minimize 自己分析更可控（反射/动态引用它分析不到）。

4. **`Class.getName()` 触发保留**：不调用业务方法，只触发类加载，既能让 Shadow 识别依赖，又不引入运行期副作用，设计精巧。

5. **全局 exclude 原始 guava**：从构建系统层面强制走 relocated 路径，比靠开发者自觉更可靠。

6. **法律合规**：shadow jar 内置 LICENSE / NOTICE，满足 Apache 2.0 重分发要求。

7. **shadow configuration 语义清晰**：明确表达"要 shaded 产物"，避免误用空壳 jar（`-empty` classifier）。

8. **借鉴成熟实践**：参考 Apache Avro 的 `GuavaClasses`，站在社区验证过的方案上，降低设计风险。

### 6.2 权衡与局限

1. **产物体积**：shadow jar 实测含约 1143 个 .class，体积不算小（虽经 minimize 裁剪）。这是隔离带来的必要代价。

2. **版本升级成本**：升级 Guava 需重新打包并全量测试；若 API 有破坏性变更，所有上层模块的 relocated 引用都要同步调整。

3. **反射/动态加载不友好**：若上层代码通过反射访问 Guava 内部类，minimize 可能误删。`GuavaClasses` 白名单是对此的部分缓解，但需人工维护。

4. **白名单维护负担**：新增使用 `GuavaClasses` 清单外的 Guava 类时，必须记得增补清单，否则 minimize 可能裁掉导致运行时 `NoClassDefFoundError`。这是隐式约定，容易遗漏（虽然有测试兜底）。

5. **`com.google.common` 之外的 Guava 包**：relocate 规则只覆盖 `com.google.common`，未覆盖 `com.google.thirdparty`（Guava 内部用）等。若上层用到这些包的类，可能未被 relocate，存在隐患。实测 shadow jar 主要是 `com.google.common.*` 子包。

6. **`-empty` jar 仍会生成**：普通 jar 任务无法关闭，只能标 classifier 为 `empty` 防误用。产物目录里会同时存在两个 jar，略增混乱。

7. **Shadow 插件版本耦合**：依赖 `com.github.johnrengelman.shadow` 第三方插件，插件本身版本升级可能带来行为变化（如 minimize 算法调整）。

8. **调试不直观**：relocate 后的栈追踪中类名是 `org.apache.iceberg.relocated.com.google.common.collect.ImmutableMap`，与 Guava 官方文档/源码对不上，新手排查问题时需要意识到这是重打包后的 Guava。

### 6.3 使用约定

为保持一致性，全仓库遵循以下约定：

1. **所有 Guava 引用走 relocated 包名**：`import org.apache.iceberg.relocated.com.google.common.*`，禁止直接 `import com.google.common.*`（全局 exclude 已在构建层面阻止）。
2. **新增 Guava 类需同步 `GuavaClasses`**：若使用了清单外的类，需在 `bundled-guava/src/main/java/org/apache/iceberg/GuavaClasses.java` 的静态块中增补 `X.class.getName();`。
3. **依赖方式统一**：`implementation project(path: ':iceberg-bundled-guava', configuration: 'shadow')`，不要直接 `implementation 'com.google.guava:guava'`。
4. **测试可用 guava-testlib**：`testImplementation libs.guava.testlib` 在本模块测试中使用，不打入 shadow jar。
