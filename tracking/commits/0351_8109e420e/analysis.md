## 总体目的

本提交是一次**反向移植（backport）**：把 Iceberg 主分支（main，对应 Flink 1.18）上引入的"Watermark 读取选项（Watermark Read Options）"特性同步到仍维护的 Flink 1.17 与 1.16 集成模块，确保两个老版本分支在 watermark 能力上与主线保持一致。Iceberg 的 Flink 集成按 Flink 大版本拆分了三套并行的 source 代码（`flink/v1.16`、`flink/v1.17`、`flink/v1.18`），主线特性发版时往往只先落在最新分支，需要后续通过 backport PR 把改动同步回去。本提交一次性同步到 1.17 与 1.16 两套代码树，所以下文每个文件路径都会出现两次（`flink/v1.17/...` 与 `flink/v1.16/...`），但改动内容几乎完全一致。

要理解这次 backport 的"特性"本身，需要先看 watermark 在 IcebergSource（Flink 1.18 FLIP-27 source）中的现有设计。原 1.18 主线提交（PR #9326 之类）已经允许用户通过 `IcebergSource.Builder.watermarkColumn(String)` / `watermarkTimeUnit(TimeUnit)` 这一对 Builder 方法配置 watermark 列：source 在 split 分配阶段会读取该列在文件元数据中的最小统计值作为 split watermark，并据此对 split 排序（早 watermark 的 split 先读），从而支持 Flink 的 watermark alignment 与按事件时间有序消费。但原实现把 `watermarkColumn` / `watermarkTimeUnit` 作为 `Builder` 的私有字段直接保存，存在两个问题：(1) 这两个参数无法通过 Flink SQL 的 `OPTIONS` / table hint 在 SQL 层面配置——SQL 用户必须改用 Table API 才能设 watermark 列，丧失了 SQL 的便利性；(2) Builder 上同时设置 `watermarkColumn` 与 `assignerFactory` 会触发 `Preconditions.checkArgument` 异常，但这个校验只在 `assignerFactory()` 方法里做，时序错乱（先设 watermark 再设 assigner 会被拒，反过来则不会），不易理解。

本次 backport 的核心改造就是把 watermark 配置从"Builder 私有字段"重构为"`FlinkReadOptions` + `FlinkReadConf` 读取选项"，使其与 Iceberg 其他读取选项（如 `split-size`、`snapshot-id`、`case-sensitive` 等）走同一条"SQL hint / table options → `readOptions` map → `FlinkReadConf` 解析 → `ScanContext`"的统一配置链路。具体新增了两个读取选项：`watermark-column`（字符串，无默认值，表示关闭 watermark 生成）与 `watermark-column-time-unit`（`TimeUnit` 枚举，默认 `MICROSECONDS`，用于 long 类型列的时间单位换算）。这样 SQL 用户可以直接 `SELECT * FROM my_table /*+ OPTIONS('watermark-column'='t1') */` 或者建表时设置 table property 来启用 watermark，无需改 Table API。同时原 `watermarkTimeUnit` 方法被重命名为 `watermarkColumnTimeUnit`（与选项 key 对齐），并移除了 `assignerFactory()` 里的不对称校验（校验保留在 `watermarkColumn()` 方法一侧，时序无关）。这是典型的 Iceberg "把 Builder 参数下沉为 ReadOptions" 的重构模式，与 `split-size`、`include-column-stats` 等已有选项保持一致风格。

配套地，本次提交还新增了 `TestHelpers.assertRecordsWithOrder` / `assertRowsWithOrder` 两个断言工具方法（用 AssertJ 的 `containsExactlyElementsOf` 做有序断言，区别于已有 `assertRecords` 的 `containsExactlyInAnyOrderElementsOf` 无序断言），并在 `TestIcebergSourceSql` 中新增 `testWatermarkOptionsAscending` / `testWatermarkOptionsDescending` 两个端到端 SQL 测试，构造两个 datafile（每个 datafile 内 2 行），通过 `watermark-column` + `split-file-open-cost` 阻止小文件合并，验证按 t1（timestamp 列，ascending）与 t2（long 列 + `MILLISECONDS` 时间单位，descending）两种排序下 split 的实际读取顺序与预期一致。两个测试方法覆盖了 watermark 选项的两种典型用法：纯 timestamp 列（默认 micro）与 long 列 + 显式 time-unit。

## 如何达成设计目的

实现路径分三层：(1) **`FlinkReadOptions` 新增两个常量**——`WATERMARK_COLUMN`（key=`watermark-column`）+ `WATERMARK_COLUMN_OPTION`（`ConfigOption<String>`，`stringType().noDefaultValue()`，未设即关闭 watermark）与 `WATERMARK_COLUMN_TIME_UNIT`（key=`watermark-column-time-unit`）+ `WATERMARK_COLUMN_TIME_UNIT_OPTION`（`ConfigOption<TimeUnit>`，`enumType(TimeUnit.class).defaultValue(TimeUnit.MICROSECONDS)`）。Flink 的 `ConfigOptions.enumType` 会自动做字符串到枚举的解析与校验。(2) **`FlinkReadConf` 新增两个 getter**——`watermarkColumn()` 用 `confParser.stringConf().option(...).flinkConfig(...).defaultValue(...).parseOptional()`（`parseOptional` 表示未设返回 null，与 `noDefaultValue` 配合表达"未配置=关闭"语义）；`watermarkColumnTimeUnit()` 用 `confParser.enumConfParser(TimeUnit.class)...parse()`（必填，有默认值）。(3) **`IcebergSource.Builder` 重构**——删除 `private String watermarkColumn` / `private TimeUnit watermarkTimeUnit = TimeUnit.MICROSECONDS` 两个私有字段；`watermarkColumn(String)` 方法改为 `readOptions.put(FlinkReadOptions.WATERMARK_COLUMN, columnName)`（写入 readOptions map）；`watermarkTimeUnit` 重命名为 `watermarkColumnTimeUnit` 并改为 `readOptions.put(FlinkReadOptions.WATERMARK_COLUMN_TIME_UNIT, timeUnit.name())`；`assignerFactory()` 中的 watermark 校验被移除（让 `watermarkColumn()` 一侧的校验成为唯一入口，时序无关）；`build()` 方法中 `contextBuilder.resolveConfig(...)` 之后新增 `FlinkReadConf flinkReadConf = new FlinkReadConf(table, readOptions, flinkConfig); String watermarkColumn = flinkReadConf.watermarkColumn(); TimeUnit watermarkTimeUnit = flinkReadConf.watermarkColumnTimeUnit();`，从 `FlinkReadConf` 读取最终生效值（与 `ScanContext.Builder.resolveConfig` 内部读取方式一致，确保 Builder API 与 SQL 两条路径都收敛到同一个 `FlinkReadConf` 来源），后续 `if (watermarkColumn != null) { contextBuilder.includeColumnStats(...) ... }` 逻辑保持不变。(4) **`ScanContext` 持久化两个字段**——构造函数新增 `watermarkColumn` / `watermarkColumnTimeUnit` 形参，新增两个 getter，`copyWithAppendsBetween` / `copyWithIncrementalScan` 两个复制方法都补上 `.watermarkColumn(...).watermarkColumnTimeUnit(...)`，`Builder` 默认值取 `FlinkReadOptions.WATERMARK_COLUMN_OPTION.defaultValue()`（即 null）与 `FlinkReadOptions.WATERMARK_COLUMN_TIME_UNIT_OPTION.defaultValue()`（即 `MICROSECONDS`），`resolveConfig` 末尾追加 `.watermarkColumn(flinkReadConf.watermarkColumn()).watermarkColumnTimeUnit(flinkReadConf.watermarkColumnTimeUnit())`——这样 `ScanContext` 通过 `FlinkReadConf` 解析后获取 watermark 配置，而非通过额外构造参数透传，保证 `ScanContext` 与 `IcebergSource.Builder` 两处对同一份 `FlinkReadConf` 解析结果一致。

## 修改详情

### `flink/v1.17/flink/src/main/java/org/apache/iceberg/flink/FlinkReadConf.java`（与 `flink/v1.16/.../FlinkReadConf.java` 同步）

**修改目的**：把 watermark 配置暴露为 `FlinkReadConf` 的 getter，让 `IcebergSource.Builder` 与 `ScanContext.Builder` 通过统一的 conf 解析链路读取。

**工作逻辑**：新增 `import java.util.concurrent.TimeUnit;`。在类末尾新增两个方法：`public String watermarkColumn()` 用 `confParser.stringConf().option(FlinkReadOptions.WATERMARK_COLUMN).flinkConfig(FlinkReadOptions.WATERMARK_COLUMN_OPTION).defaultValue(FlinkReadOptions.WATERMARK_COLUMN_OPTION.defaultValue()).parseOptional()`——`parseOptional` 让未配置时返回 null 而非抛异常，与 `noDefaultValue` 语义对齐；`public TimeUnit watermarkColumnTimeUnit()` 用 `confParser.enumConfParser(TimeUnit.class).option(FlinkReadOptions.WATERMARK_COLUMN_TIME_UNIT).flinkConfig(FlinkReadOptions.WATERMARK_COLUMN_TIME_UNIT_OPTION).defaultValue(FlinkReadOptions.WATERMARK_COLUMN_TIME_UNIT_OPTION.defaultValue()).parse()`——`enumConfParser` 会自动把字符串如 `"MILLISECONDS"` 解析为 `TimeUnit.MILLISECONDS`，非法值会抛 `IllegalArgumentException`。

### `flink/v1.17/flink/src/main/java/org/apache/iceberg/flink/FlinkReadOptions.java`（与 `flink/v1.16/.../FlinkReadOptions.java` 同步）

**修改目的**：声明 `watermark-column` 与 `watermark-column-time-unit` 两个 Flink `ConfigOption`，作为 SQL / table property / Builder 三条配置路径的共同契约。

**工作逻辑**：新增 `import java.util.concurrent.TimeUnit;`。在类末尾新增四个常量：`public static final String WATERMARK_COLUMN = "watermark-column";` 与 `public static final ConfigOption<String> WATERMARK_COLUMN_OPTION = ConfigOptions.key(PREFIX + WATERMARK_COLUMN).stringType().noDefaultValue();`——`PREFIX` 是 `FlinkReadOptions` 已有的 `"read."` 前缀，故完整 key 为 `read.watermark-column`，`noDefaultValue()` 表示不设该选项即视为关闭 watermark；`public static final String WATERMARK_COLUMN_TIME_UNIT = "watermark-column-time-unit";` 与 `public static final ConfigOption<TimeUnit> WATERMARK_COLUMN_TIME_UNIT_OPTION = ConfigOptions.key(PREFIX + WATERMARK_COLUMN_TIME_UNIT).enumType(TimeUnit.class).defaultValue(TimeUnit.MICROSECONDS);`——`enumType` 让 Flink 自动做字符串到 `TimeUnit` 的解析校验，默认 `MICROSECONDS` 与原 `Builder.watermarkTimeUnit` 默认值一致（Iceberg timestamp 内部存储为 micros，故 long 列按 micros 解读能直接对齐 timestamp 列）。

### `flink/v1.17/flink/src/main/java/org/apache/iceberg/flink/source/IcebergSource.java`（与 `flink/v1.16/.../IcebergSource.java` 同步）

**修改目的**：把 watermark 配置从 `Builder` 私有字段重构为通过 `readOptions` map + `FlinkReadConf` 解析，同时移除不对称的 `assignerFactory` 校验。

**工作逻辑**：核心改动集中在 `Builder` 内部：(1) 新增 `import org.apache.iceberg.flink.FlinkReadConf;`（之前已 import `FlinkReadOptions`，但未 import `FlinkReadConf`）。(2) 删除字段 `private String watermarkColumn;` 与 `private TimeUnit watermarkTimeUnit = TimeUnit.MICROSECONDS;`——这两个字段不再由 Builder 直接持有，改由 `readOptions` map 携带。(3) `assignerFactory(SplitAssignerFactory)` 方法中删除 `Preconditions.checkArgument(watermarkColumn == null, "Watermark column and SplitAssigner should not be set in the same source");`——该校验原本只在 `assignerFactory()` 中做，导致"先 watermark 后 assigner 被拒、先 assigner 后 watermark 不被拒"的时序依赖 bug，现统一在 `watermarkColumn()` 一侧校验。(4) `watermarkColumn(String)` 方法保留 `Preconditions.checkArgument(splitAssignerFactory == null, ...)` 校验，但赋值改为 `readOptions.put(FlinkReadOptions.WATERMARK_COLUMN, columnName);`。(5) `watermarkTimeUnit(TimeUnit)` 方法重命名为 `watermarkColumnTimeUnit(TimeUnit)`（与选项 key 命名对齐），赋值改为 `readOptions.put(FlinkReadOptions.WATERMARK_COLUMN_TIME_UNIT, timeUnit.name());`——存字符串名而非枚举，符合 `readOptions` 是 `Map<String, String>` 的契约。(6) `build()` 方法中，原 `contextBuilder.resolveConfig(table, readOptions, flinkConfig);` 之后新增 `FlinkReadConf flinkReadConf = new FlinkReadConf(table, readOptions, flinkConfig); String watermarkColumn = flinkReadConf.watermarkColumn(); TimeUnit watermarkTimeUnit = flinkReadConf.watermarkColumnTimeUnit();`——这是关键：从 `FlinkReadConf` 重新解析 watermark 值，确保 Builder API 设置的值（已写入 `readOptions`）与 SQL hint 设置的值走同一条解析路径，最终在 `if (watermarkColumn != null) { contextBuilder.includeColumnStats(Sets.newHashSet(watermarkColumn)); ... }` 分支中使用。这样 Builder API 与 SQL 两条入口收敛到同一份 `FlinkReadConf`，行为一致。

### `flink/v1.17/flink/src/main/java/org/apache/iceberg/flink/source/ScanContext.java`（与 `flink/v1.16/.../ScanContext.java` 同步）

**修改目的**：让 `ScanContext` 持久化 watermark 配置，并在 `copyWith*` 复制方法中保留 watermark 字段，确保 incremental scan 等场景下 watermark 行为不丢失。

**工作逻辑**：(1) 新增 `import java.util.concurrent.TimeUnit;`。(2) 类字段新增 `private final String watermarkColumn;` 与 `private final TimeUnit watermarkColumnTimeUnit;`。(3) 私有构造函数新增两个对应形参（紧跟 `maxAllowedPlanningFailures` 之后），并赋值给字段。(4) 新增两个 getter `watermarkColumn()` 与 `watermarkColumnTimeUnit()`。(5) `copyWithAppendsBetween(Long, long)` 与 `copyWithIncrementalScan(...)` 两个复制方法在 `Builder` 链式调用中追加 `.watermarkColumn(watermarkColumn).watermarkColumnTimeUnit(watermarkColumnTimeUnit);`，保证复制后的 `ScanContext` 仍带 watermark 配置（incremental scan 仍按 watermark 排序 split）。(6) `Builder` 类新增字段 `private String watermarkColumn = FlinkReadOptions.WATERMARK_COLUMN_OPTION.defaultValue();`（即 null）与 `private TimeUnit watermarkColumnTimeUnit = FlinkReadOptions.WATERMARK_COLUMN_TIME_UNIT_OPTION.defaultValue();`（即 `MICROSECONDS`）。(7) `Builder` 新增两个 setter `watermarkColumn(String)` 与 `watermarkColumnTimeUnit(TimeUnit)`。(8) `Builder.resolveConfig(Table, Map, ReadableConfig)` 末尾追加 `.watermarkColumn(flinkReadConf.watermarkColumn()).watermarkColumnTimeUnit(flinkReadConf.watermarkColumnTimeUnit());`——这是 SQL 路径的入口：`resolveConfig` 内部已构造 `FlinkReadConf`，直接复用其解析结果，把 watermark 值塞进 `ScanContext`。(9) `Builder.build()` 方法在构造 `ScanContext` 时新增 `watermarkColumn, watermarkColumnTimeUnit` 两个实参。

### `flink/v1.17/flink/src/test/java/org/apache/iceberg/flink/TestHelpers.java`（与 `flink/v1.16/.../TestHelpers.java` 同步，差异仅在 v1.17 显式新增 `import org.assertj.core.api.Assertions;`）

**修改目的**：新增"有序断言"工具方法，因为 watermark 排序后 split 的读取顺序是确定的，需要严格按顺序断言而非无序断言。

**工作逻辑**：把原 `assertRecords(List<Row>, List<Record>, Schema)` 方法体提取为 `private static List<Row> convertRecordToRow(List<Record>, Schema)`——该私有方法把 `Record` 列表通过 `DataStructureConverter` 转为 `Row` 列表，是公共的转换逻辑。基于此重构 `assertRecords` 为 `List<Row> expected = convertRecordToRow(...); assertRows(results, expected);`。新增 `public static void assertRecordsWithOrder(List<Row> results, List<Record> expectedRecords, Schema schema)`：`List<Row> expected = convertRecordToRow(...); assertRowsWithOrder(results, expected);`。新增 `public static void assertRowsWithOrder(List<Row> results, List<Row> expected)`：`Assertions.assertThat(results).containsExactlyElementsOf(expected);`——AssertJ 的 `containsExactlyElementsOf` 要求结果列表与期望列表**严格按顺序**完全相等（数量、顺序、元素），区别于已有 `assertRows` 用的 `containsExactlyInAnyOrderElementsOf`（仅要求数量与元素集合相等，顺序无关）。v1.17 版本额外显式 `import org.assertj.core.api.Assertions;`，v1.16 版本该 import 已存在故 diff 不含此行。

### `flink/v1.17/flink/src/test/java/org/apache/iceberg/flink/source/TestIcebergSourceSql.java`（与 `flink/v1.16/.../TestIcebergSourceSql.java` 同步）

**修改目的**：新增端到端 SQL 测试，验证通过 SQL OPTIONS 设置 `watermark-column` / `watermark-column-time-unit` 能正确驱动 split 排序。

**工作逻辑**：(1) 新增多个 import，包括 `org.apache.flink.table.api.TableEnvironment`、`org.apache.iceberg.DataFile` / `FileFormat` / `Schema` / `Table`、`org.apache.iceberg.data.GenericAppenderHelper` / `GenericRecord` / `Record`、`org.apache.iceberg.flink.TestFixtures` / `TestHelpers`、`org.apache.iceberg.types.Types`、`org.junit.Test` 等。(2) 新增 `SCHEMA_TS` 静态 schema：`new Schema(required(1, "t1", Types.TimestampType.withoutZone()), required(2, "t2", Types.LongType.get()))`——t1 是 timestamp 列（默认 micros 时间单位），t2 是 long 列（可配 time-unit）。(3) `before()` 方法重构：把 `getTableEnv()` 缓存为 `TableEnvironment tableEnvironment` 局部变量复用；新增 `tableEnvironment.getConfig().set("table.exec.resource.default-parallelism", "1")`——并行度设为 1 保证 split 顺序可断言（多并行会打乱顺序）。(4) 新增 `private Record generateRecord(Instant t1, long t2)`：构造一条 `Record`，t1 由 `Instant.atZone(ZoneId.systemDefault()).toLocalDateTime()` 转为 `LocalDateTime`（Iceberg timestamp without zone 的 Java 表示），t2 直接是 long。(5) 新增 `private List<Record> generateExpectedRecords(boolean ascending)`：创建表 `TestFixtures.TABLE_IDENTIFIER`（schema 为 `SCHEMA_TS`）；定义 `baseTime = 1702382109000L`；用 `GenericAppenderHelper`（Parquet 格式）写两个 datafile，每个 datafile 含 2 条记录——`dataFile1` 的两条记录 t1 时间戳分别为 `baseTime` 与 `baseTime - 10s`（早期时间），`dataFile2` 的两条记录 t1 时间戳分别为 `baseTime + 14s` 与 `baseTime + 12s`（晚期时间）；同时 t2 的值设计为：`dataFile1` 的 t2 是 `baseTime + 30天` 与 `baseTime + 35天`（新 long），`dataFile2` 的 t2 是 `baseTime - 30天` 与 `baseTime - 35天*61`（旧 long）。这样：按 t1（ascending micros）排序 split 应该 `dataFile1` 先读（早期时间），按 t2（descending milliseconds，但 watermark 排序总是按 split watermark 升序，这里通过 watermark 的 t2 值大小决定顺序——dataFile2 的 t2 min 更小所以先读）排序应该是 `dataFile2` 先读。根据 `ascending` 参数返回 `dataFile1 → dataFile2`（ascending）或 `dataFile2 → dataFile1`（descending）的预期顺序。每个 datafile 内部 2 条记录的相对顺序由 datafile 内部顺序决定，故预期列表保持 datafile 写入顺序。(6) `testWatermarkOptionsAscending()`：调用 `run(ImmutableMap.of("watermark-column", "t1", "split-file-open-cost", "128000000"), "", "*")`——`split-file-open-cost=128000000`（128MB）是为了阻止 Iceberg 把两个小 datafile 合并成一个 split（合并后 watermark 排序就失去意义）；`run` 是基类方法返回查询结果的 `List<Row>`。断言用 `TestHelpers.assertRecordsWithOrder(...)` 严格有序断言。(7) `testWatermarkOptionsDescending()`：`run(ImmutableMap.of("watermark-column", "t2", "watermark-column-time-unit", "MILLISECONDS", "split-file-open-cost", "128000000"), "", "*")`——验证 long 列 + 显式 `MILLISECONDS` 时间单位下，split 按 t2 的 millisecond 值排序（dataFile2 的 t2 更小，先读）。两个测试覆盖了 watermark 选项的两种典型用法：纯 timestamp 列（默认 micros，无需 time-unit）与 long 列 + 显式 time-unit。

## 小结

本次提交是把主线 Flink 1.18 的"Watermark 读取选项"特性 backport 到 1.17 与 1.16 两个维护分支。核心改动是把 watermark 配置从 `IcebergSource.Builder` 的私有字段重构为标准的 `FlinkReadOptions` + `FlinkReadConf` 读取选项链路，新增 `watermark-column`（字符串，无默认值=关闭）与 `watermark-column-time-unit`（`TimeUnit` 枚举，默认 `MICROSECONDS`）两个选项，让 SQL 用户能通过 `OPTIONS` table hint 直接启用 watermark 排序，无需改用 Table API。重构同时修复了原 `Builder.assignerFactory()` 中 watermark 校验的时序依赖问题（先 watermark 后 assigner 才会触发异常），改为只在 `watermarkColumn()` 一侧校验，时序无关。`ScanContext` 持久化两个字段并在 `copyWithAppendsBetween` / `copyWithIncrementalScan` 复制方法中保留，保证 incremental scan 仍按 watermark 排序。`Builder.build()` 中通过重新构造 `FlinkReadConf` 读取 watermark 最终值，确保 Builder API 与 SQL 两条入口收敛到同一份解析结果。测试侧新增 `assertRecordsWithOrder` / `assertRowsWithOrder` 有序断言工具，并新增两个端到端 SQL 测试覆盖 timestamp 列（ascending）与 long 列 + `MILLISECONDS`（descending）两种 split 排序场景。1.17 与 1.16 两套代码树改动几乎完全一致，仅在 `TestHelpers.java` 的 `Assertions` import 上有微小差异（1.17 显式新增，1.16 已存在）。
