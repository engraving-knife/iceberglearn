## 总体目的

本提交是 Flink 1.20 模块引入四步序列（1032-1035）的第二步。在前一个提交（1032）中，`flink/v1.19/` 被整体重命名为 `flink/v1.20/`，以便 v1.20 继承 v1.19 的 git 历史。但这导致仓库中暂时缺少 v1.19 模块，而 Iceberg 仍需继续维护 Flink 1.19（它尚未进入 End of Life）。

本提交的目的是把 v1.19 模块"加回来"：从前一步生成的 `flink/v1.20/` 目录拷贝出全部文件，重新创建 `flink/v1.19/` 子模块。由于此时 v1.20 的内容与原 v1.19 完全相同（1032 仅做了重命名、未改内容），所以这一步恢复出的 v1.19 与迁移前的 v1.19 在内容上一致。提交说明中的 "coping" 是 "copying" 的笔误。

这样做的整体效果是：v1.20 拥有了从 v1.19 沿袭而来的完整历史链（因为它是 `git mv` 来的），而 v1.19 则作为一份新拷贝重新存在，后续可以独立维护。这种"先移走再拷回来"的手法是 Git 中为新建模块保留历史的常用做法。

## 如何达成设计目的

从 `flink/v1.20/` 目录完整复制所有文件到新建的 `flink/v1.19/` 目录。由于是新增文件，git 将其全部识别为新增（add），共新增 325 个文件，内容与 v1.20 完全一致。这一步不涉及任何代码逻辑改动，纯粹是文件复制。

## 修改详情

### `flink/v1.19/**`（新增）

**修改目的**：重新创建 Flink 1.19 子模块，使 Iceberg 在引入 1.20 的同时继续保留对 1.19 的支持。

**工作逻辑**：从 `flink/v1.20/` 完整拷贝出 325 个文件到 `flink/v1.19/`，覆盖的内容与 1032 中重命名的文件集合完全对应，包括：
- `build.gradle` 构建脚本（此时内部 `flinkMajorVersion` 仍为 `1.19`，因为 1032 只是改名、未改内容，而原 v1.19 的 build.gradle 里写的就是 1.19）。
- `flink-runtime/` 下的 `LICENSE`、`NOTICE`。
- `flink/src/main/java/` 下全部主源码类。
- `flink/src/test/java/` 下全部测试类。
- `flink/src/jmh/java/` 下的基准测试。
- `META-INF/services/` 下的 SPI 声明文件。

所有文件均为新增，内容与同时期的 `flink/v1.20/` 完全相同。

## 小结

- **成效**：恢复了 v1.19 子模块，使仓库同时拥有 v1.18、v1.19、v1.20 三个 Flink 子模块，且 v1.20 继承了 v1.19 的历史。
- **影响范围**：新增 `flink/v1.19/` 目录及其下 325 个文件，无代码内容变更（与 v1.20 完全一致）。
- **回迁到 1.4.x 的注意事项**：与 1032 类似，不适合单独回迁。这是 Flink 1.20 引入序列的中间步骤，单独 cherry-pick 到 1.4.x 会因为缺少 1032 的重命名前置而无法对齐仓库状态。若 1.4.x 需要该改动，应作为整组（1032-1035）一并评估。
