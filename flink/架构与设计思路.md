# Iceberg Flink 模块架构与设计思路

> 本文档基于 `flink/v1.17` 实际源码分析整理，覆盖多版本子模块的整体设计与最新版本（v1.17）的实现细节。源码根目录：`/Users/fengxiaohang/trae/iceberglearn/flink/`。

## 1. 模块定位

Iceberg 整体分层自下而上为：`api`（公共契约）→ `core`（引擎无关的表格式内核：元数据、快照、扫描、事务）→ `data`/`parquet`/`orc`/`arrow`（读写与向量化）→ 引擎集成层（`flink`、`spark`、`mr`、`pig`）→ 各云与 Catalog 实现（`aws`、`hive-metastore`、`nessie` 等）。

`flink` 模块属于**引擎集成层**，职责是把 Iceberg 表格式能力暴露给 Apache Flink（Table API/SQL 与 DataStream API）。它在 Iceberg 内核之上做适配，自身不持有表元数据存储与文件格式实现，而是：

- 将 Flink 的 `AbstractCatalog`/`DynamicTableFactory`/`DynamicTableSource`/`DynamicTableSink` 等 SPI 适配到 Iceberg 的 `Catalog`/`Table`/`TableScan`/`AppendFiles`/`RowDelta`/`ReplacePartitions`。
- 实现 Flink FLIP-27 的 `Source` 接口（`IcebergSource`）与流式 sink 算子链（`IcebergStreamWriter` + `IcebergFilesCommitter`），提供 exactly-once 语义的批/流读写。
- 把 Flink 的谓词/投影/limit 下推、changelog 模式（INSERT/UPDATE_BEFORE/UPDATE_AFTER/DELETE）、UPSERT（equality fields）等能力映射到 Iceberg 语义。

## 2. 多版本结构说明

### 2.1 为什么有多版本子模块

Flink 在 1.15 → 1.16 → 1.17 → 2.x 之间持续演进 Table/Connector API、Source/Sink SPI（FLIP-27/FLIP-143）、状态后端、序列化框架等，存在不兼容变更。Iceberg 需要同时支持多个 Flink 主版本，因而为每个版本维护一份源码。

### 2.2 子模块组织方式

每个版本目录（如 `flink/v1.17/`）下固定两个子工程，由 `flink/v1.17/build.gradle` 声明并通过 `settings.gradle` 注册为 Gradle 子项目：

| 子工程 | Gradle 项目名 | 职责 |
| --- | --- | --- |
| `flink/` | `iceberg-flink-1.17` | Iceberg-Flink 集成主代码（Java）。`compileOnly` 依赖 Flink 1.17 的 streaming/table/avro/connector 等包，`implementation` 依赖 `api`/`core`/`data`/`parquet`/`orc`/`hive-metastore`。 |
| `flink-runtime/` | `iceberg-flink-runtime-1.17` | shade 胖包，把主模块 + 各云 Catalog 实现打成一个可投递的 jar，并 `relocate` 隔离 parquet/orc/avro 等依赖冲突，包含集成测试源集。 |

`settings.gradle` 通过 `flinkVersions`/`knownFlinkVersions` 系统属性决定纳入哪些版本；`gradle.properties` 中 `knownFlinkVersions=1.15,1.16,1.17`、`defaultFlinkVersions=1.16`。注意 Flink 不像 Spark 那样按 Scala 版本二次分叉（Flink 1.17 起统一 binary，不再区分 scala 版本）。

### 2.3 版本间差异（实际源码对比）

- `flink/v1.15`、`v1.16`、`v1.17` 三个版本的 `org/apache/iceberg/flink/` 顶层包**文件列表完全一致**（均为 26 个文件 + 6 个子包），`source/` 子包结构也一致。差异主要在内部对 Flink API 变化的兼容性调整（如 `FlinkCompatibilityUtil`、状态后端、序列化器签名等），目录级不可见。
- `flink/v1.17` 是当前 `knownFlinkVersions` 的最新正式版本，包含完整的 FLIP-27 source 实现（`IcebergSource`/`IcebergSourceReader`/`ContinuousIcebergEnumerator`/`SplitAssigner`）、RANGE 分布 shuffle（`sink/shuffle/DataStatisticsCoordinator`）等较新特性。
- `flink/v2.1` 目录存在但**完全为空**（仅 `flink/` 子目录，无任何源码文件），属于为未来 Flink 2.x 预留的脚手架，当前 `settings.gradle` 未将其纳入构建（`knownFlinkVersions` 中也不含 2.1）。

## 4. 核心类与设计模式

### 4.1 适配器 / 包装模式（核心思想）

整个模块本质是**适配器层**：把 Iceberg 引擎无关抽象包装成 Flink SPI。典型链路：

- `FlinkCatalog` 包装 `org.apache.iceberg.catalog.Catalog` + `CachingCatalog`，并把 Flink database 映射到 Iceberg namespace（结合 `baseNamespace`）；
- `FlinkDynamicTableFactory` 把 Flink 表属性/source/sink 请求适配为 `IcebergTableSource`/`IcebergTableSink`；
- `FlinkSink` 内部根据写入语义选择 `table.newAppend()`/`newRowDelta()`/`newReplacePartitions()`，并用 Iceberg 的 `TaskWriter`/`RollingDataWriter` 写文件；
- `FlinkSource`/`IcebergSource` 把 Flink 谓词/投影/limit 转成 Iceberg `Expression`/`Schema`，并构建 `BatchScan`/`IncrementalAppendScan`。

### 4.2 Builder 模式

`FlinkSink.Builder`（`forRowData`/`forRow`/`builderFor`）链式收集表加载、schema、equality 字段、分发模式、uidPrefix 等；`FlinkSource.Builder`/`IcebergSource.Builder` 收集扫描上下文、reader 函数、assigner 工厂等。Builder 内部懒加载 `Table`（避免重复打开 `TableLoader`）。

### 4.3 模板方法

`AbstractIcebergEnumerator` 实现 `SplitEnumerator` 的协调骨架（reader 等待队列、split 请求/退回、completed split 跟踪），把 split **发现**与**分配**分别委托给 `ContinuousSplitPlanner` 与 `SplitAssigner`；`StaticIcebergEnumerator`/`ContinuousIcebergEnumerator` 提供批/流两种 plan 调用策略。

### 4.4 策略模式

- **Split 分配策略**：`SplitAssigner` 接口支持 `SimpleSplitAssigner`（无序）、`OrderedSplitAssigner`（按 snapshot 顺序/event time 对齐）、本地性感知等多种策略，可插拔。
- **数据分发策略**：`FlinkSink` 按 `write.distribution-mode` 选择 NONE/HASH/RANGE：HASH 用 `PartitionKeySelector`/`EqualityFieldKeySelector` 按 equality 字段分发；RANGE 用 `sink/shuffle` 的 `DataStatisticsOperator` + `DataStatisticsCoordinator` 收集全局统计后做自定义分区。
- **写入语义策略**：`FlinkSink` 按 overwrite/equality 决定 append/rowDelta/replacePartitions。

### 4.5 门面（Facade）

`Actions`（`flink/actions`）作为表维护动作门面，当前主要提供 `RewriteDataFilesAction`（基于 Flink DataStream 重写数据文件）。相比 Spark 的 `SparkActions`，Flink 侧动作集合较精简。

### 4.6 算子链 + Checkpoint 集成

`IcebergStreamWriter`（`ChainingStrategy.ALWAYS`，可与上游 chain）产出 `WriteResult`，`IcebergFilesCommitter`（单并行度）在 `notifyCheckpointComplete` 时提交。利用 Flink checkpoint 语义实现 exactly-once：只有 checkpoint 成功后才提交，失败回滚只丢弃未提交文件。

### 4.7 FLIP-27 Source 抽象

`IcebergSource<T> implements Source<T, IcebergSourceSplit, IcebergEnumeratorState>`，提供 `SourceReader`（`IcebergSourceReader`）、`SplitEnumerator`（静态/连续）、split 与 enumerator 状态的 `SimpleVersionedSerializer`。标记 `@Experimental` 表示 API 尚不稳定，与旧版 `FlinkSource`（基于 InputFormat + `StreamingMonitorFunction`）并存。

### 4.8 SPI / 服务发现

`FlinkCatalogFactory`（`type=iceberg`）与 `FlinkDynamicTableFactory`（`factoryIdentifier=iceberg`）通过 Flink 的 factory SPI 被发现，使 `CREATE CATALOG` 与 `CREATE TABLE ... WITH ('connector'='iceberg')` 均可使用。

## 5. 关键流程

### 5.1 Flink 读 Iceberg 表

两条路径并存：

**A. 旧版 `FlinkSource`（InputFormat + 流式算子）**

1. `FlinkSource.forRowData()` Builder 收集 `TableLoader`/`Table`/`ScanContext`。
2. 批模式：构建 `FlinkInputFormat`（`InputFormatSourceFunction`），Flink 调度 `FlinkInputSplit`（每个 split 对应一个 `CombinedScanTask`），executor 用 `RowDataFileScanTaskReader`/`DataIterator` 读文件。
3. 流模式：`StreamingMonitorFunction`（单并行度）周期性扫描新 snapshot，把新 `CombinedScanTask` 分发给 `StreamingReaderOperator`（多并行度）读取。

**B. 新版 `IcebergSource`（FLIP-27）**

1. `IcebergSource.Builder` 收集 `TableLoader`/`ScanContext`/`ReaderFunction`/`SplitAssignerFactory`/`SerializableComparator`。
2. `createEnumerator`：批模式用 `StaticIcebergEnumerator`（启动时一次性 `FlinkSplitPlanner.plan`）；流模式用 `ContinuousIcebergEnumerator`（周期性 `ContinuousSplitPlannerImpl.discoverSplits`，基于 `startSnapshotId`/`endSnapshotId` 决定有界/无界）。
3. `SplitAssigner`（`Simple`/`Ordered`）管理已发现 split 的分配，enumerator 通过 `SplitRequestEvent` 与 reader 通信，无可用 split 时 reader 进入 `CompletableFuture` 等待。
4. `createReader`：`IcebergSourceReader` 持有 `IcebergSourceSplitReader`，调用 `ReaderFunction`（`RowDataReaderFunction`/`AvroGenericRecordReaderFunction`/`MetaDataReaderFunction`）把 split 转为记录批次（`ArrayBatchRecords`/`ListBatchRecords`，由 `DataIteratorBatcher`/`ArrayPoolDataIteratorBatcher` 控制批大小与对象池）。
5. `IcebergSourceRecordEmitter` 把记录发射给下游，`IcebergSourceReaderMetrics` 上报扫描指标。
6. 状态恢复：`IcebergSourceSplitSerializer`/`IcebergEnumeratorStateSerializer` 序列化 split 与 enumerator 进度，支持 checkpoint 恢复。

### 5.2 Flink 写 Iceberg 表

1. **入口**：`IcebergTableSink.getSinkRuntimeProvider` → `FlinkSink.builderFor(...)`（或用户直接 `FlinkSink.forRowData`）；从 TableSchema 主键提取 equality 字段 id（`checkAndGetEqualityFieldIds`）。
2. **分发**：`distributeDataStream` 按 `write.distribution-mode`：
   - `NONE`：不分发；
   - `HASH`：按 `EqualityFieldKeySelector`/`PartitionKeySelector` 分发，保证同 key 同 subtask；
   - `RANGE`：插入 `DataStatisticsOperator`，由 `DataStatisticsCoordinator`（`OperatorCoordinator`）聚合各 subtask 的 `MapDataStatistics`，下发 `AggregatedStatistics` 后做自定义分区（数据聚类）。
3. **写入**：`appendWriter` 创建 `IcebergStreamWriter`（`RowDataTaskWriterFactory` → `PartitionedDeltaWriter`/`UnpartitionedDeltaWriter`/`BaseDeltaTaskWriter`），每个 subtask 写数据文件 + 必要的 delete 文件。checkpoint barrier 到达时 `prepareSnapshotPreBarrier` flush 当前 writer 产出 `WriteResult`（含 `DataFile[]`/`DeleteFile[]`），重建新 writer。
4. **提交**：`appendCommitter` 创建单并行度 `IcebergFilesCommitter`：
   - 缓存每个 checkpoint 的 `WriteResult`，`snapshotState` 时通过 `FlinkManifestUtil` 写成 `DeltaManifests` 序列化到状态后端；
   - `notifyCheckpointComplete` 时按 checkpoint id 升序合并提交（`AppendFiles`/`RowDelta`/`ReplacePartitions`），在 snapshot summary 写入 `flink.max-committed-checkpoint-id`/`flink.job-id`/`flink.operator-id`；
   - 恢复时跳过已提交 checkpoint，避免重复提交。
5. **终止**：`appendDummySink`（`DiscardingSink`）吃掉 committer 的 `Void` 输出，便于 Flink 调度。
6. **Changelog/UPSERT**：`IcebergTableSink` 支持 `ChangelogMode`（INSERT/UPDATE_BEFORE/UPDATE_AFTER/DELETE），`RowKind` 决定写数据或 delete 文件；equality fields 触发 `RowDelta` + equality delete，实现 CDC/UPSERT。

### 5.3 SQL DDL 与 Catalog 流程

1. `CREATE CATALOG cat WITH ('type'='iceberg', 'catalog-type'='hive'/'hadoop'/'rest', ...)`：Flink 通过 SPI 创建 `FlinkCatalogFactory`，加载 hive/hadoop 配置，构造 `CatalogLoader` 与 `FlinkCatalog`（含 `baseNamespace`、`CachingCatalog`）。
2. `CREATE TABLE cat.db.tbl (...) PARTITIONED BY (...)`：`FlinkCatalog.createTable` 把 Flink `CatalogTable` 转成 Iceberg `Schema`/`PartitionSpec`，调用底层 `Catalog.createTable`。
3. `INSERT INTO / SELECT FROM cat.db.tbl`：Flink 通过 `FlinkCatalog` 拿到 `CatalogTable`，`FlinkDynamicTableFactory`（catalog 模式）创建 `IcebergTableSource`/`IcebergTableSink`。
4. `ALTER TABLE`：`FlinkAlterTableUtil` 把 Flink `TableChange` 转成 Iceberg `UpdateSchema`/`UpdatePartitionSpec`。

## 6. 与其他模块的关系

- **`iceberg-api`**：消费 `Catalog`/`Table`/`TableScan`/`AppendFiles`/`RowDelta`/`ReplacePartitions`/`Snapshot`/`Expression` 契约。
- **`iceberg-core`**：使用 `BatchScan`/`IncrementalAppendScan`/`IncrementalChangelogScan`/`TableOperations`/`CachingCatalog`/`ManifestFile`/`Snapshot` 等内核实现；`SerializableTable` 用于把表序列化到 executor。
- **`iceberg-data`/`iceberg-parquet`/`iceberg-orc`**：`data/` 子包基于这些模块构建 Flink 类型读写器（`FlinkParquetReaders`/`FlinkParquetWriters`/`FlinkOrcReader`/`FlinkAvroReader`）。Flink 侧目前**不使用 arrow 向量化**（与 Spark 不同）。
- **`iceberg-common`**：复用跨引擎公共工具与配置。
- **`iceberg-hive-metastore`**：Hive catalog 实现与测试 fixtures。
- **`iceberg-bundled-guava`**：shade guava，避免与 Flink 自带版本冲突。
- **下游**：Flink Table API/SQL 与 DataStream API 通过 SPI 消费；用户在 SQL 或 DataStream 作业中使用。

## 7. 设计亮点与权衡

### 7.1 exactly-once 基于 Flink checkpoint

写入流程的核心是 `IcebergStreamWriter`（多并行度，每个 checkpoint flush 一次）+ `IcebergFilesCommitter`（单并行度，`notifyCheckpointComplete` 时提交）。通过把 `WriteResult` 序列化为 `DeltaManifests` 存入状态后端，并在 Iceberg snapshot summary 记录 `flink.max-committed-checkpoint-id`，实现：失败恢复时跳过已提交 checkpoint、不同作业恢复不重复提交。这是 Flink 流式写入 Iceberg 的语义基石，相比 Spark 的批式提交更适配流式场景。

### 7.2 双轨 Source：旧版与 FLIP-27 并存

旧版 `FlinkSource`（InputFormat + `StreamingMonitorFunction`）稳定可用；新版 `IcebergSource`（FLIP-27，`@Experimental`）采用 enumerator/reader/assigner 分离的现代架构，支持更灵活的 split 分配（有序、本地性、event time 对齐）与更好的 checkpoint 恢复。这种双轨过渡是 Flink 生态演进的典型模式，给用户迁移时间，但增加了维护成本。

### 7.3 可插拔 SplitAssigner

`SplitAssigner` 接口把"split 如何分配给 reader"从 enumerator 解耦，支持 `Simple`/`Ordered`/本地性感知/event time 对齐等多种策略，无需改 enumerator 即可扩展。enumerator 通过 `CompletableFuture` + `AtomicReference` 实现异步等待：无可用 split 时 reader 进入等待，新 split 发现后唤醒。

### 7.4 RANGE 分布的全局统计协调

`sink/shuffle` 子包实现了一套基于 `OperatorCoordinator` 的全局数据统计机制：各 subtask 的 `DataStatisticsOperator` 上报 `MapDataStatistics`，`DataStatisticsCoordinator` 聚合后下发 `AggregatedStatistics`，驱动自定义分区器做数据聚类。这使得 Flink 写入可以按 RANGE 分布（类似 Spark 的 sort-based shuffle），写出更均衡的数据文件，而无需依赖 Iceberg 自己实现分布式 shuffle。

### 7.5 CatalogLoader + TableLoader 可序列化

`CatalogLoader` 与 `TableLoader` 都是可序列化接口，把 catalog 配置与表标识带到 executor 端按需加载/缓存表。这避免 driver 单点加载所有表元数据，适配 Flink 的分布式执行模型。`SerializableTable` 进一步把表元数据序列化广播。

### 7.6 适配器层薄、内核厚

与 Spark 模块一致，真正复杂的逻辑（任务合并、split 切分、删除文件合并、文件格式读写、事务提交、乐观锁）都在 `core`/`data`/`parquet`/`orc` 中，`flink` 模块只做"Flink 概念 ↔ Iceberg 概念"的翻译。这使得引擎适配层可以随 Flink API 变化快速重写而不影响内核。

### 7.7 权衡

- **多版本源码重复**：与 Spark 类似，Flink 各版本目录间源码高度重复，差异主要在兼容性细节；社区以 `core` 收敛公共逻辑缓解。
- **强依赖 Flink 内部 API**：`IcebergStreamWriter`/`IcebergFilesCommitter` 继承 `AbstractStreamOperator`，使用 `StateInitializationContext`/`OperatorCoordinator` 等 Flink runtime API，升级版本需同步调整。
- **FLIP-27 source 仍 Experimental**：`IcebergSource` 标记 `@Experimental`，API 尚未完全稳定，生产用户多仍在旧版 `FlinkSource`。
- **动作能力较 Spark 精简**：`flink/actions` 仅 `RewriteDataFilesAction`，缺少 Spark 那样完整的 expire/rewrite-manifests/remove-orphan-files/migrate/snapshot 动作集（部分能力需通过 SQL 或外部工具完成）。
- **不使用 arrow 向量化**：Flink 侧读取不基于 Arrow 列向量，向量化程度低于 Spark，大宽表扫描吞吐相对受限。
- **`flink/v2.1` 为空壳**：仅有 `flink/` 占位目录，无源码，需等社区为 Flink 2.x 适配后填充（当前 `knownFlinkVersions` 也不含 2.1）。
